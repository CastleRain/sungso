# 양정커피 회원 전용 매출 분석

기존 `sohee/combined`의 자료와 React·Recharts·TanStack Table·Lucide 화면을 재사용한 회원 전용 앱이다. 디저트 준비는 조회한 토스 상세와 저장한 메뉴 구성을 사용해 브라우저 메모리에서 다시 계산한다. 작업실·포트폴리오는 보존하고 작업실에 매출 앱 링크를 추가했다. 최신 분석의 Firebase 이전과 회원 접근 규칙 반영을 완료했다. 웹 배포 결과는 검증 기록의 운영 연결 항목을 따른다.

## 화면과 실행

| 경로 | 주요 판단 |
|---|---|
| `/sungso/sohee/sales/changes/` | 대시보드: 매출 요약·일별/누적·요일/시간·큰 주문 영향, 운영 인사이트의 동요일 비교·매출 분포·메뉴 집중도 |
| `/sungso/sohee/sales/overview/` | 매출 내역: 일별 금액·결제 순건수·여러 날짜 달력·월별 원장 |
| `/sungso/sohee/sales/menus/` | 메뉴 전략: 수량·금액·판매 빈도·기록일당 수량·요일 변화, 월별/시간대 상세와 메뉴 구성 설정 |
| `/sungso/sohee/sales/prep/` | 디저트 준비: 날짜·준비 성향·메뉴별 직접 조절, 단계별 일반 준비와 확정 주문, 과거 초과/부족·예측 검증 |
| `/sungso/sohee/sales/data/` | 이전 직접 링크 호환용 자료 기준·원본 검증/저장. 주 탐색에서 제외 |

각 경로의 HTML을 생성하므로 해시 라우팅이나 서버의 SPA fallback 없이 직접 접근·새로고침·뒤로/앞으로 이동이 가능하다. `/sales/`는 대시보드다. 매출 내부의 일반 링크 클릭은 History API로 화면만 전환하여 회원 셸·조회한 자료·분석 날짜를 유지한다. 매번 sungso 인증 화면을 다시 띄우거나 Firebase 분석을 다시 내려받지 않는다. 새 탭·직접 진입·새로고침에는 기존 공통 인증을 그대로 적용한다. 분석 화면은 작업실로 돌아갈 수 있고, 대시보드의 ‘과거 변화와 비교 근거’ 옆 패널에서 기존 포트폴리오 예시로 이동한다. 매출을 포트폴리오로 복제하지 않는다.

루트에서:

```sh
npm ci --prefix apps/sohee/sales
node apps/sohee/sales/preview.mjs --qa
```

`http://127.0.0.1:4176/sungso/sohee/workspace/`는 **가상 자료 전용 화면 QA**다. 실제 계정·DB·토스 요청을 보내지 않는다. 테스트 전용 연결 모듈은 QA 빌드에만 포함한다.

`node apps/sohee/sales/preview.mjs`는 `4177`에서 실제 공통 회원 인증을 사용하는 로컬 셸을 제공한다. 운영 Firebase에 저장된 최신 분석을 읽는다. 원본 갱신 API는 같은 PC의 `8791`로만 프록시하며 서버 실행은 [서비스 안내](../../../services/sohee/README.md)를 따른다.

독립 프로토타입 Vite만 실행한 `4175` 대신 위 통합 미리보기를 사용한다. 소희 프로토타입의 기존 Sites 파일은 보존했다. 루트 `config/apps.json`은 생성된 회원 셸과 코드만 등록한다. 대문·모든 앱에서 소희 작업실로 이동하며 기존 공유 홈 저장 스키마는 유지한다. 프로토타입이나 비공개 아카이브 전체를 공개 허용 목록에 넣지 않는다.

## 화면 구성

기본 표현 계층은 `src/polish.css`와 `src/charts.jsx`, 데스크톱의 한 화면 배치는 `src/compact.css`에서 관리한다. 메뉴·준비 화면의 기존 밀도 스타일에 `src/insights.css`·`src/prep-owner.css`를 더하고, 공통 기간 선택은 `src/period-controls.css`로 구성한다. 넓은 화면에서는 주요 지표와 판단을 한 화면에 모으고 긴 표는 내부에서 이동하며 상세는 옆 패널로 연다. 작은 화면은 글자 크기를 유지하고 문서 세로 스크롤을 허용한다. 실제로 확인한 화면 크기와 한계는 [디자인 검증](design-qa.md)과 [검증 기록](verification.md)을 따른다.

**분석 기간**에는 이전/다음 월 이동·월 선택, 최근 7일·최근 30일·최신 월 전체·전체 기간 바로가기, 연속 기간/떨어진 여러 날짜를 고르는 달력을 제공한다. 최근 기간은 컴퓨터의 오늘이 아니라 **저장된 마지막 완결일까지의 달력일**이며 수집 시작일 밖으로 나가지 않는다. 현재 선택과 자료 기준을 함께 표시한다. 하단 매출 달력의 기본 클릭은 일별 메뉴 상세만 열고, ‘여러 날짜 선택’ 모드에서는 다른 달의 날짜도 추가/해제한다. 부분일 포함 조건과 날짜 선택은 매출 내부 이동·뒤로/앞으로 이동·명시적 분석 재조회 동안 유지한다. 새로고침/새 진입과 상단 양정커피 홈 클릭 시 최신 월 전체로 초기화하며 선택은 메모리에만 보관한다.

**대시보드**는 선택 기간 실매출·완결된 매출 기록일·일평균·결제 순건수·결제 1건당 실매출을 먼저 보여준다. 일별/선택일 누적 Recharts 그래프, 메뉴 TOP 5, 요일별 기록일당 매출/표본, 시간대, 토스 큰 주문 비중과 제외 금액을 비교한다. 매출 그래프는 날짜·요일·금액을 툴팁과 아래 읽기 영역에 표시하며 포인터·키보드·날짜 이동 버튼을 지원한다. 평일·주말·큰 주문 포함·부분일·음수 순매출을 의미색과 범례로 구분한다.

‘운영 인사이트’ 옆 패널에는 같은 요일의 결제 순건수와 건당 실매출 변화, 완결 기록일의 매출 중앙값·가운데 50% 범위, 상위 5개 메뉴의 금액 비중을 제공한다. 평균에 큰 매출일이 미치는 영향이나 준비 우선 메뉴를 검토하는 단서다. 고객 수·이익률·실제 품절/로스·매출 변화 원인으로 해석하지 않는다. 기존 기록일·이전 기간 비교는 ‘집계 기준·기록일’, 대량 주문/아메리카노/포트폴리오 근거는 ‘과거 변화와 비교 근거’에서 확인한다.

**매출 내역**은 날짜별 정산과 조회를 위한 달력·일별 원장·펼쳐보는 월별 원장이다. **메뉴 전략**은 어떤 메뉴를 얼마나 꾸준히 준비할지 판단하는 화면으로 분리한다. 7행씩 보는 메뉴 표에는 선택 기간 수량·단위·금액·금액 비중·판매 빈도를 표시한다. 금액 비중의 분모는 메뉴 집계 합계다. 옆 판단 영역에서 메뉴를 고르면 순판매가 있는 날, 기록일당 순수량, 이전 동요일 대비 수량 변화, 하루 판매 중간값과 요일별 평균/표본을 본다. 메뉴 또는 ‘선택 메뉴 분석’을 누르면 전체 월별 변화·선택일 주문 시간대·날짜별 수량/금액을 Drawer에서 확인한다. 표의 금액/수량과 토스 상세 기반 빈도 지표는 자료 범위가 다를 수 있어 구분해 표시한다.

메뉴 빈도·하루 수량은 **메뉴 상세가 존재하는 토스 완결 결제 기록일**을 분모로 쓴다. 명시적인 0개 상세도 관측으로 인정하고, 상세가 하루 통째로 누락된 경우는 제외한다. 해당 메뉴의 순수량이 양수인 날을 판매일로 세며 환불은 부호를 유지한다. 페이히어·부분일에는 일별 메뉴 값을 만들지 않는다. 매장 전체의 상세는 있지만 해당 메뉴 판매가 없는 날은 순수량 0으로 포함하므로 메뉴 진열일·판매 가능일·품절률을 뜻하지 않는다. 같은 이름이어도 단위가 다르면 수량을 합치지 않는다.

**디저트 준비**는 별도의 준비 날짜와 적게/기준/넉넉히 준비 성향을 선택한 뒤 일반 판매분을 직접 조절한다. 평균 예상량과 조절할 정수 준비량을 구분하며 오전·12–16시·16시 이후의 단계별 일반 준비량을 보여준다. 제조 소요 시간은 준비 시작을 검토하는 보조값이다. 확정된 예약·큰 주문 수량은 사용자가 별도로 추가하고 수령 시각을 확인하며, 일반 판매 시간대에 임의로 나누지 않는다. 실제 매출 거래나 운영 생산 기록을 생성하지 않는다.

메뉴별 판단 영역은 과거 판매와 현재 준비 수량의 차이를 보여준다. 여기의 평균 초과/부족은 **학습 표본에 현재 수량을 대입한 참고 비교**이며 실제 폐기·품절 또는 순차 검증 성능이 아니다. ‘예측 검증’ 탭은 과거 날짜마다 그 전날까지의 자료만 사용한 판매량 예측 오차와 준비 성향별 초과/부족을 별도로 표시한다. ‘요일 비교’와 ‘표본·계산 기준’, 기간을 고르는 ‘과거 판매와 비교하기’도 제공한다. 전체 메뉴 준비 성향을 바꾸면 수동 조절을 초기화하고, 메뉴별 성향 버튼은 해당 메뉴만 조절한다. 날짜 변경은 수동 수량과 확정 주문을 초기화한다. 이 조절값은 화면 메모리에만 유지하며 CSV로 내려받을 수 있고 Firebase에 생산/예약 기록으로 저장하지 않는다.

자료 기준은 하단 작은 팝오버에서 수집 기간·완결일·부분일을 확인한다. ‘저장된 분석 다시 불러오기’는 Firebase 조회만 수행하며 토스 수집을 시작하지 않는다. 기존 데이터 관리 경로는 호환을 위해 남겨두지만 네 메뉴에 표시하지 않는다.

연속/개별 날짜의 메뉴·메뉴 시간·대량 주문은 토스 완결일 상세만 사용한다. Payhere 월별 메뉴를 날짜로 배분하지 않는다. 저장된 결제 시간대는 월 단위이므로 날짜 선택 시 메뉴 주문 시작 시각으로 명확히 구분해 표시한다. 기존 매출 요약의 이전 기간 비교는 선택 완결일의 시작~끝 길이만큼 이전으로 이동한다. 새 운영 인사이트·메뉴 전략의 동요일 비교는 최소 28일이면서 선택 구간과 겹치지 않는 7일 배수만큼 이전 날짜에 대응시킨다. 완결일 7일 이상, 양쪽 결제 기록일 각각 5일 이상, 대응 날짜·POS 출처가 모두 확인되어야 비교한다. 메뉴 수량 비교는 양쪽의 토스 상세 관측도 필요하며 이전 평균이 0 이하이면 증감률을 제시하지 않는다.

공통 분석 기간과 디저트 준비의 계산 기준은 독립적이다. 날짜 필터는 과거 실적 조회에 적용하고, 준비 모델은 저장된 마지막 완결 토스 날짜를 기준으로 최근 자료를 사용한다. 준비 날짜를 바꿔도 그 날짜까지 새 자료를 수집하거나 미래 자료를 만들어 넣지 않는다.

소희 작업실·포트폴리오·매출은 같은 사이트에서 제공하는 Pretendard Variable을 사용한다. 다른 sungso 앱의 글꼴은 유지한다. 좁은 화면도 네 메뉴를 바로 표시하고 내부 표 스크롤, 준비표의 고정 메뉴 열을 사용한다.

버튼·선택창·달력·날짜/시간·수량·체크박스·슬라이더·접기·파일/암호 입력은 Mantine 8.3.18로 구성하고 sungso 테마 토큰을 연결한다. React 19.1.1을 유지하며 라이브러리의 브라우저 기본 입력 외형을 그대로 노출하지 않는다. 선택창은 회원 화면 트리 안에서 열려 로그아웃 시 함께 제거된다.

[시안 대조와 반응형 검증](design-qa.md)에 가상 자료 캡처와 확인 범위를 기록했다. 실제 매출은 디자인 시안이나 캡처에 사용하지 않았다.

## 일별 상세와 메뉴 집계 수정

대시보드와 매출 내역의 **일평균 매출**은 선택 날짜 중 `record_day=true`인 완결일의 실매출 합계를 해당 날짜 수로 나눈 값이다. 순매출이 0원이어도 결제 기록일이면 포함한다. 부분일·미수집일·`record_day=false` 날짜는 분자와 분모에서 제외한다. `record_day=false`에는 환불만 기록된 날도 있을 수 있으므로 휴무나 0원으로 단정하지 않는다. 해당 완결 기록일이 없으면 평균은 ‘—’다. 선택 기간의 **총매출**은 기존 집계 범위를 유지하므로 평균에 제외한 환불/부분일 금액도 원래 조건에 따라 반영될 수 있다.

‘매출 기록일’의 날짜 확인 또는 ‘집계 기준·기록일’에서 포함/제외 날짜와 계산식을 확인한다. 근무·출퇴근 기록은 없으므로 실제 근무일시를 만들지 않는다. 토스 완결일은 저장된 메뉴 주문 기록 중 가장 이른 시간대와 가장 늦은 시간대를 별도 상세로 제공한다. 수량 또는 금액이 있는 시간별 집계이며 보존된 환불 기록도 포함할 수 있다. 정확한 첫/마지막 거래 시각, 개점·폐점·근무 시간이나 전체 영업 시간을 뜻하지 않으며, 페이히어와 부분일의 메뉴 시각을 추정하지 않는다.

매출 내역 상단의 전체·토스·페이히어로 출처를 나눈다. 이 필터는 현재 매출 내역에만 적용되며 선택 출처의 요약·기록일·달력·원장·CSV를 함께 좁힌다. 선택 기간에 해당 출처의 날짜가 전혀 없으면 그 출처의 최신 월 전체로 이동한다. 출처를 다른 화면으로 전달하거나 원본을 수정하지 않는다.

상단 분석 기간을 바꾸면 달력은 마지막 선택 날짜가 있는 달로 맞춰진다. 월 전체 상태에서 달력 월을 넘기면 상단 월도 바뀌며, 연속/개별 기간 상태에서는 선택한 달 사이를 이동해도 분석 기간을 유지한다. 여러 날짜 선택 모드는 다른 달에서도 날짜를 추가/해제한다. 상단 날짜 팝업도 현재 기간의 마지막 달에서 열린다.

표와 달력에서 메뉴 조회 가능 여부를 표시한다. 토스의 메뉴 보기·부분일·상세 없음과 페이히어의 월별만을 구분한다. 페이히어 상세의 월별 메뉴 바로가기는 해당 월을 적용하고, 메뉴 화면은 그 월의 모든 출처를 집계한다.

매출 내역의 날짜 또는 달력을 누르면 토스 완결일의 판매 메뉴·수량·단위·금액을 옆 패널로 확인한다. 월 전체 필터는 그대로 유지한다. 메뉴 날짜가 없는 Payhere, 저장 상세에서 제외된 부분일, 상세가 없는 날은 이유를 표시하고 월별 합계로 메뉴를 만들어 넣지 않는다.

메뉴 전략의 **메뉴 이름·수량 수정**은 판매 상품 → 구성 메뉴의 두 단계로 표시한다. 원본 상품 하나가 팔릴 때 반영할 **집계할 메뉴·들어있는 수량·수량 단위**를 직접 지정하고 Firebase에 저장한다. 집계할 메뉴는 기존 메뉴에서 고르거나 새로운 이름을 입력할 수 있으며, 저장한 새 이름은 다음 상품 설정의 선택 후보에 나타난다. 미리보기는 실제 원본 이름 1팩 → 지정한 메뉴 4개처럼 표시한다. 별도 낱개 상품도 같은 메뉴/단위와 수량 1로 지정하면 합산되며, 같은 대상에 연결된 다른 설정을 보여준다. 이름에 숫자를 쓰는 것만으로 수량을 추정하지 않는다. 같은 이름과 같은 단위만 합산하며 원본과 매출액은 보존한다. 수정은 과거 전체 기간과 앞으로 같은 원본 이름으로 들어오는 자료에 적용된다. 원본 이름이 달라지면 사용자가 별도로 연결해야 한다.

`sohee_menu_rules/{SHA256(원본 이름)}`는 인증된 활성 회원이 공유하는 별도 설정이다. `sourceName`, `targetName`, `unit`, 정수 `multiplier`(1–100), `enabled`, `revision`, `updatedBy`, 서버 `updatedAt`을 저장한다. 읽기로 문서를 만들지 않고, 저장 시 transaction으로 기존 revision을 비교한다. 충돌 시 입력은 유지하며 닫고 다시 열면 최신 서버 설정을 읽는다. 원본 집계 복원은 설정을 비활성화하며 삭제하지 않는다. 새 토스 분석을 올려도 이 컬렉션을 덮어쓰지 않는다. 다른 화면의 변경은 재조회 또는 편집 패널을 다시 열 때 가져온다.

디저트 준비표·요일 비교·선택일 실제 판매·준비 CSV에도 저장한 메뉴 이름과 수량 배수를 적용한다. 현재 준비 모델은 원본의 일별 부호 있는 메뉴 수량에서 큰 주문을 분리하고, 사용자 구성대로 환산·같은 이름/단위끼리 합산한 뒤 음수를 0으로 제한해 학습한다. 설정은 한 번만 적용하고 매출 금액은 바꾸지 않는다. 팩·개·세트의 단위를 섞지 않으며 낱개 구성을 모르는 단위는 실물 총개수로 추정하지 않는다. 표본 부족·최근 미판매 메뉴는 참고용으로 구분해 사용자가 포함할 때만 준비표에 더한다.

`src/demand-model.mjs`는 최근 28일 관측 판매 평균과 56일 같은 요일 정보를 섞은 후보를 순차 비교한다. 과거 검증에서 충분한 개선이 있었을 때만 후보를 선택하며, 자료가 부족하거나 차이가 없으면 단순 최근 평균을 유지한다. 준비 성향은 관찰 분포의 35/50/70 분위수를 지정 단위의 정수로 올린 비교안이다. 원가·부족 비용이 없어 최적 생산량으로 제시하지 않는다. 일반 준비량은 시간 비중에 따라 합계가 보존되도록 나누며, 시각별 큰 주문 수량이 없어 큰 주문이 있었던 날짜 전체를 시간 비중에서 제외한다. 시간 표본이 없으면 배분하지 않는다.

새 계산과 메뉴 구성 적용 후의 순차 검증은 **조회한 자료에 대한 메모리 계산**이다. 원본 거래·Firebase의 불변 분석 버전·기존 저장 예측을 수정하거나 새 모델을 외부로 전송하지 않는다. 기존 원본 메뉴/판매단위 기준의 검증 결과는 ‘기존에 저장한 예측 검증도 확인하기’에서 별도로 유지한다. 이전 예측이 단순 평균보다 부정확했던 결과를 숨기거나 새 통합 메뉴의 성능으로 바꾸지 않는다. 새 검증의 오차·초과/부족도 단위별로 분리하고 표본 수를 함께 표시한다. 자세한 입력·비교 조건·계산식과 한계는 [준비 초안의 계산과 검증](forecast-methods.md)을 따른다.

같은 원본 메뉴 설정을 반복 저장하면 같은 해시 문서를 갱신한다. 매출 거래를 추가하지 않으며 각 화면은 항상 원본에 최신 설정을 한 번 적용한다. 메뉴 구성 설정의 회원 공통 Firebase 저장과 준비 화면의 임시 수량 조절을 구분한다.

## 수동 갱신

요청할 때 Codex가 이 컴퓨터에서 토스를 열어 새 원본을 받아 검증하고 Firebase에 저장한다. 로컬 갱신 도구와 기존 관리 경로를 유지하며 일반 대시보드에서 수집을 시작하지 않는다. 예약 수집·앱 실행 시 자동 수집·토스 Open API를 사용하지 않는다. 페이히어는 과거 자료로 유지한다. [구체적인 절차](../../../services/sohee/manual-update.md)를 따른다.

## 데이터·보호 경계

- 빌드에는 코드·공통 테마·라이브러리만 들어간다. 실제 매출 JSON/CSV/XLSX, 원본 HTML 보고서와 QA 자료는 운영 번들에 포함하지 않는다.
- `shared/firebase/boot.mjs`가 Google 활성 회원 확인 후 앱을 시작한다. 기존 SDK 10.12.0과 `homehunt-private-cloud` 앱을 재사용하고 `syncAppAuth` 후에만 조회한다.
- Firestore `sohee_sales/current`의 현재 버전과 `sohee_sales_versions/{hash}/chunks/{index}`를 서버에서 읽는다. 누락 조각·해시 불일치를 거부하며 브라우저 디스크 캐시를 새로 만들지 않는다.
- 원본 분석은 두 활성 역할 회원만 get 가능하고 브라우저의 list·쓰기·삭제는 금지한다. 계정 전환/권한 변경/로그아웃 시 공통 정리로 React·메모리·진행 중 요청을 정리한다. 늦은 응답은 무시한다.
- 조회와 첫 진입은 시딩·쓰기·수집을 하지 않는다. 저장된 분석 재조회와 새로운 토스 원본 수집을 명확히 구분한다.
- `sohee/` Git 제외는 루트에서도 고정했다. 실제 원본은 그대로 보존했다. 화면에서 따로 관찰된 합계를 거래로 생성하지 않았다.

## 해석

디저트는 당일 판매·이월 0 기준이다. 메뉴 시각과 준비 예측은 토스 완결일만 사용하며 큰 주문을 분리한다. 화면은 선택 예측·단순 최근 평균·요일 후보의 평균 절대 오차(MAE), 단위별 준비 성향의 초과/부족, 표본 부족·참고 메뉴를 구분해 표시한다. 준비 수량 조정은 화면 메모리에서만 유지하며 CSV로 내려받을 수 있다. 미래 판매나 확정 생산량을 보장하지 않는다.

수정하지 않은 4구는 판매 표에서 1팩, 준비 합계에서 실물 4개로 표시한다. 매출 기록 없는 날을 휴무로 단정하지 않고, 개인 기여 시점·운영 변경일·매출 변화의 원인은 미확인으로 표시한다. 비용 자료가 없어 순이익을 계산하지 않는다.
