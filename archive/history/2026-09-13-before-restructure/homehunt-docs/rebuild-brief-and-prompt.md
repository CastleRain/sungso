# HomeHunt 리빌딩 브리프 · 개발 프롬프트

> 목적: 기존 기능과 데이터 원칙을 유지하되, 화면 구조와 대시보드는 자유롭게 다시 설계해 **집을 사기 전 필요한 근거를 최대한 모으는 부부용 집 탐색 도구**로 고도화한다.

## 현재 기준선

- 현재 화면은 지도 중심 UI 3.0.4, 로컬 API 계약은 2.5.1이다.
- 서울·경기 공식 아파트 카탈로그 17,851개, 국토부 매매·전월세 조회, 방문 기록, 최대 4개 목적지 통근 구조, 분양·청약 화면과 Telegram 알림 파이프라인이 구현되어 있다.
- 로컬에서는 실제 국토부·NAVER·통근 API를 쓸 수 있지만, GitHub Pages에서는 안전한 서버 호출과 개인 데이터 동기화가 아직 완성되지 않았다.
- 청약홈·LH는 활용승인/권한 상태를 다시 확인해야 하며, 승인되지 않은 공급원을 가짜 공고로 채우면 안 된다.
- 실거래의 `72%`는 실제 완료율이 아니라 원격 조회 단계의 고정 표시다. 최초 5년 조회가 멈춘 것처럼 보이는 문제가 있다.

# 제품의 본질

HomeHunt는 단순 부동산 대시보드나 포털 복제품이 아니다.

“성우와 소희가 서울·경기에서 여러 회사·주요 목적지에 실제로 다닐 수 있는 집을 지도에서 찾고, 관심 후보·방문 기록·실거래 변화·분양 기회를 한 곳에서 판단하는 부부용 집 탐색 운영 도구”다.

사용자 흐름은 다음과 같다.

목적지 등록
→ 예산·평형·세대수·연식·생활 조건 설정
→ 지도에서 후보 지역과 단지를 탐색
→ 관심 후보 저장·비교
→ 실제 방문 기록
→ 방문 당시 대비 현재 실거래 변화 확인
→ 분양·청약 기회·자격·알림 확인
→ 최종 의사결정

# 기존 화면을 그대로 따라 하지 말 것

현재 UI는 지도 중심·사이드 패널·여섯 메뉴·조건 드로어 구조를 갖고 있다. 이 구조가 최선이라고 가정하지 않는다.

- “통계 카드가 많은 리포트형 대시보드”로 만들지 않는다.
- 숫자는 사용자가 다음 행동을 결정하는 데 도움이 될 때만 쓴다.
- 긴 카드가 세로로 쌓여 스크롤만 길어지는 구조를 피한다.
- 첫 화면에는 지금 확인할 가치가 큰 정보가 보여야 한다.
  - 내 조건에서 실제 가격 확인이 된 후보 지역
  - 새로 생긴 분양·청약 기회
  - 최근 저장한 관심 후보와 방문 집의 가격 변화
  - 통근, 실거래, 청약 자격 중 아직 확인하지 못한 항목
- 정보를 한 페이지에 억지로 넣지 말고 지도, 비교 보드, 타임라인, 상세 패널, 컨텍스트 드로어 등 더 적절한 형태로 나눈다.
- 먼저 정보 우선순위와 핵심 사용자 흐름을 설계하고, 그 이유를 짧게 설명한 뒤 구현한다.

# 반드시 접근 가능해야 하는 메뉴

다음 여섯 개 개념은 데스크톱에서 “더보기”에 숨기지 않고 모두 접근 가능해야 한다.

1. 집 찾기
2. 내 기록
3. 실거래
4. 분양·청약
5. 사용 안내
6. 연결 상태

메뉴 배치, 보조 문구, 대시보드 형태, 화면 전환 방식은 자유롭게 설계할 수 있다. 예를 들어 지도 워크스페이스, 오늘의 판단 보드, 후보 비교 보드, 방문·관심·분양 타임라인을 조합해도 된다.

# UX 원칙

## 지도 우선

- 집 찾기와 내 기록에서는 지도가 가장 큰 비중을 차지한다.
- 검색·필터가 지도를 밀어내지 않는다.
- 필터는 기본적으로 짧은 칩과 검색 바로만 보여주고, 상세 조건은 필요할 때 여는 드로어·패널·모달로 제공한다.
- 후보가 밀집한 곳은 숫자가 든 원형 클러스터로 보인다. 확대하면 개별 가격 핀으로 자연스럽게 전환한다.
- 방문 집은 별표, 관심 후보는 하트, 분양은 깃발, 목적지는 별도 핀으로 명확히 구분한다.
- 결과 수, 실제 가격 확인 수, 지도 좌표 확인 수, 좌표 미확인 수를 서로 혼동하지 않게 표시한다.

## 한 화면에서 판단

- 사용자가 스크롤을 많이 하지 않아도 현재 결론과 다음 행동을 알 수 있어야 한다.
- 데스크톱은 가로 공간을 적극 활용하고, 모바일은 지도 유지 + 바텀시트 중심으로 설계한다.
- 비교·근거·차트·예측처럼 깊은 정보는 상세 패널 또는 하위 화면으로 이동한다.
- 결과 0건이면 “없음”만 말하지 말고 가격·면적·세대수·연식·통근 중 어떤 조건이 병목인지 알려준다.

## 기본 브라우저 UI 금지

사용자에게 기본 버튼, select, number spinner, range slider, date picker, datalist, confirm dialog를 그대로 노출하지 않는다.

- UI 라이브러리를 써도 기본 테마를 그대로 사용하지 않는다.
- 검색, 숫자 입력, 날짜, 토글, 드롭다운, 툴팁, 모달, 로딩, 빈 상태까지 하나의 제품 디자인 시스템으로 통일한다.
- `9억 3,000만원`, `9.3억`, `9억 3천만원`, `93,000만원`을 같은 금액으로 해석하고 일관되게 표시한다.
- 다만 키보드 조작, 포커스, ESC 닫기, ARIA, 모바일 터치 영역은 유지한다.

# 유지·고도화할 핵심 기능

## 1. 집 찾기

- 서울·경기 공식 아파트 카탈로그 약 17,851개 검색
- 단지명·동네·주소 자유검색, 유사/오타 보정, 동명 단지 구분
- 예산, 전용면적/평형, 세대수, 연식, 거래 유형, 통근 조건
- 최대 4개 목적지 등록
- 후보 지도 클러스터·가격 핀·방문·관심·분양·목적지 레이어
- 후보의 실제 실거래 평균, 면적, 세대수, 연식, 통근 확인 상태
- 관심 저장, 비교, 방문 기록, 실거래 상세로 연결

통근 원칙:

- 직선거리는 후보 선별용일 뿐 실제 통근시간이 아니다.
- 실제 경로가 확인되지 않은 후보를 `60분 이내 충족`으로 처리하지 않는다.
- Kakao는 넓은 후보 선별, TMAP은 사용자가 고른 소수 후보 최종 검증, NAVER Directions는 자동차 조건에 쓴다.
- TMAP의 작은 일일 한도를 우회하거나 자동으로 소진하지 않는다.
- 목적지별 시간, 최악 통근, 가중 평균, 환승·도보 부담을 함께 보여준다.
- 장기적으로 목적지별 교통수단·출근시각·허용시간·방문 요일을 독립 저장할 수 있게 구조화한다.

## 2. 내 기록과 비교

- 실제 방문 집 CRUD: 방문일, 현장 확인 가격, 면적, 층, 장점·단점, 메모, 태그, 방문자
- 지도·목록·비교 보기
- JSON 백업·복원
- 방문일 전후의 같은 면적 실거래와 현재 실거래를 비교
- 관심 후보, 방문 집, 분양 공고를 출처가 섞이지 않게 같은 비교 흐름으로 확장

비교는 단순 표가 아니라 의사결정 도구여야 한다. 최근 실거래, 방문 당시 가격, 현재 대비 변화, 면적, 세대수, 연식, 통근, 역 접근성, 장단점, 메모, 데이터 출처, 미확인 항목을 상황에 맞게 비교한다.

## 3. 실거래

- 국토부 매매·전월세 실거래
- 정확한 단지·전용면적별 1년·3년·5년 이력
- 평균 계약가격, 평균 평당가격, 거래량, 최근 실제 계약, 월별 추세
- 방문 당시와 현재의 같은 면적 실거래 비교
- 품질 게이트와 시간 순서 백테스트를 통과한 경우에만 6개월 참고 예측

현재의 `72%` 고정 진행표시는 반드시 개선한다.

- 실제 완료 월수 또는 퍼센트 없는 정직한 `조회 중` 표시를 쓴다.
- 가능하면 최근 12개월을 먼저 보여주고 3년·5년 데이터를 점진적으로 추가한다.
- 단지 확인 → 캐시 확인 → 국토부 월별 자료 → 면적 분류 → 차트·예측 계산 단계를 보여준다.
- 경과시간, 취소, 재시도, 캐시 사용 여부, 부분 실패 월과 원인을 표시한다.
- 면적·거래유형·기간을 바꾸면 요약·차트·예측·최근 거래가 같은 데이터 범위로 즉시 갱신된다.

## 4. 분양·청약

- 청약홈 아파트·잔여세대·임의공급, LH 분양주택·신혼희망타운, SH 공식 분양 공고
- 서울·경기 범위, 지역·동네·가격·평형·세대수·접수상태·신혼 조건 필터
- 관심·읽음·일정·원문 링크·ICS·Telegram 알림
- 청약 준비도와 가점 참고

공급원 상태를 다음처럼 명확히 구분한다.

- 정상 수집
- 정상 0건
- 첫 기준선 수집 중
- 승인 대기
- 인증 실패
- 형식 변경
- 일시 장애

신혼부부 특별공급·신혼희망타운은 공식 구조화 근거가 있을 때만 확정 표시한다. 실제 경쟁률·공급군·배정 규칙 데이터가 없으면 당첨 확률 퍼센트를 만들지 말고 `신청 준비 / 확인 필요 / 조건 미충족`과 부족한 항목을 보여준다.

# 집 구매 판단을 위한 데이터 확장

사용자의 진짜 목적은 “내 예산과 조건으로 갈 수 있는 지역·아파트가 어디까지인지”와 “지금 사도 되는지”를 최대한 많은 근거로 판단하는 것이다.

따라서 단지 상세 또는 후보 상세에서 아래 정보를 **출처·시점·확정 여부**와 함께 모을 수 있는 구조를 만든다.

### 우선 데이터 축

1. 가격
   - 국토부 실제 매매·전월세
   - 동일 평형의 최근 계약, 평균, 거래량, 시간 흐름
   - 분양가, 현재 실거래, 인근 유사 단지 실거래를 분리 비교
   - 현재 매물/호가는 실거래와 절대 섞지 않고 별도 `매물·호가` 축으로 표현

2. 단지 기본 정보
   - 세대수, 준공연도, 동수, 최고층, 주차, 난방, 관리, 용적률·건폐율 등
   - K-apt 등 공식·허용된 원천을 우선 연결한다.

3. 생활·입지
   - 역 출입구 기준 보행거리와 시간
   - 버스, 학교·어린이집, 병원·마트·공원 등
   - 추정값과 실제 경로·공식 데이터 값을 구분한다.

4. 미래 변화 요인
   - 인근 입주 물량, 분양 공급, 정비사업, 지역 가격지수, 교통 계획
   - 확인 가능한 원천과 기준일이 있을 때만 표시한다.

5. 개인 판단
   - 성우·소희의 방문 메모, 장단점, 통근, 관심 상태, 비교 결과

### 예산 범위 탐색

집 찾기의 결과는 단순 후보 목록을 넘어야 한다.

- `9억 3천만원 이하 · 전용 20평 이상 · 500세대 이상 · 20년 이내` 같은 조건에서 실제 가격 확인이 된 단지가 어느 시·구·동까지 분포하는지 지도에서 보여준다.
- 지역별로 `조건 통과 단지 수 / 실거래 확인 수 / 좌표 확인 수 / 가격 범위 / 최근 변화`를 보여준다.
- 조건을 완화하거나 강화했을 때 탐색 가능 지역이 어떻게 넓어지거나 줄어드는지 직관적으로 보여준다.
- 단, 평균 실거래가 통과는 “현재 그 가격에 살 수 있는 매물이 있다”는 뜻이 아님을 명확히 표시한다.

### WeCost 재무·대출 시뮬레이션 연동

HomeHunt의 집 찾기는 가격 조건만 통과했다고 `살 수 있는 집`으로 판단하면 안 된다. 같은 Firebase 프로젝트의 `wecost/`에는 결혼·저축·가용 현금·대출·월 상환 한도를 계산하는 별도 앱이 있다. 이 데이터를 안전하게 **읽기 전용 재무 스냅샷**으로 연결해, 집 후보마다 필요한 자금과 월 상환 부담을 함께 판단한다.

현재 WeCost의 원천은 다음과 같다.

- `wecost_settings/main`: 결혼일, 목표 집 가격, 월 상환 한도, 부모 지원금과 반영 여부
- `wecost_savings/main`: 성우·소희의 현재 저축과 월 저축액
- `wecost_items`: 결혼 비용 계획·납부·잔액
- `wecost_adjustments`: 가용 현금에 더하거나 빼는 조정 항목
- `wecost_loans`: 대출금, 금리, 기간, 거치, 상환 방식, 활성 여부

WeCost의 기존 계산은 결혼일까지 예상 저축에서 결혼 비용, 선택한 지원금, 조정액을 반영해 가용 현금을 만들고, 활성 대출의 월 상환액과 총 집 예산을 계산한다. HomeHunt는 이 계산을 별도로 조금 다르게 복제하지 말고 공용 `financial snapshot` 또는 공용 계산 모듈을 통해 같은 결과를 사용한다.

구현 원칙:

- WeCost가 재무 원천 데이터의 소유자다. HomeHunt는 기본적으로 읽기만 하며, 후보를 클릭했다고 WeCost의 목표 집 가격·대출·저축 데이터를 자동 변경하지 않는다.
- HomeHunt는 현재 가용 현금, 기존 활성 대출 월 상환액, 월 상환 한도, 기준일, 마지막 동기화 시각만 필요한 최소 범위로 읽는다.
- Firebase Authentication과 household 권한이 준비되기 전에는 금융 데이터를 공개 컬렉션이나 공개 JSON으로 복제하지 않는다.
- 읽기 권한이 없거나 동기화가 실패하면 추정값을 만들지 않고 `WeCost 연결 필요` 상태와 WeCost로 이동하는 버튼을 보여준다.
- 사용자가 명시적으로 `이 후보로 자금 계획 보기`를 눌렀을 때만 후보 가격을 시나리오에 반영한다.
- 후보별 시나리오 저장은 원본 WeCost 대출을 덮어쓰지 않는 별도 개인 시나리오로 저장하며, 향후에는 인증된 household 범위로 제한한다.

후보 상세와 비교 보드에 다음을 제공한다.

1. **구매 자금 구성**
   - 기준 가격: 국토부 실거래 평균 / 최근 실거래 / 사용자가 입력한 매물 호가 중 무엇인지 명시
   - 가용 현금
   - 취득세·중개수수료·등기·이사·수리비 등 부대비용: 사용자가 입력하거나 `미포함`으로 명확히 표시
   - 필요 대출액

2. **대출 시나리오**
   - 금리, 고정·변동 여부, 기간, 거치, 상환 방식, 기존 대출 반영 여부를 사용자가 수정 가능한 시나리오로 제공
   - 월 상환액, 기존 대출을 포함한 월 총상환액, WeCost 월 상환 한도 대비 비율, 현금 여유를 표시
   - 후보 A/B/C의 필요 대출·월 상환·현금 잔여를 나란히 비교
   - `안정 / 주의 / 한도 초과 / 정보 부족`처럼 감당 상태를 구분

3. **정직한 한계**
   - 이 계산은 자금 계획 시뮬레이션이며 은행 대출 승인·한도·DSR·LTV·취득세 확정값이 아니다.
   - DSR·LTV·규제 지역·소득·기존 부채·주택 보유 수 등은 최신 공식 규정과 금융기관 심사가 필요하므로, 검증된 입력이 없으면 `확인 필요`로 표시한다.
   - 금리는 고정 사실처럼 하드코딩하지 않는다. 사용자가 입력한 시나리오 값 또는 출처·기준일이 있는 금리 정보만 사용한다.

UX 요구:

- 집 찾기 지도에서 후보를 열면 `실거래`, `통근`, `생활 정보`와 함께 작고 명확한 `자금 계획` 상태가 보인다. 재무 숫자가 아직 연결되지 않았으면 거대한 빈 카드 대신 연결 행동을 제안한다.
- 상세 화면에서는 WeCost에서 계산한 현재 예산과 이 후보 선택 시의 차이를 즉시 보여준다.
- `WeCost에서 조건 수정`은 WeCost의 집 시뮬레이션 탭으로 이동하고, 수정 뒤 HomeHunt로 돌아오면 최신 스냅샷으로 갱신한다.
- 지도 탐색 중에는 재무 정보가 주인공이 되지 않게 하고, 후보 선택·비교·최종 판단 단계에서 깊게 보여준다.
- 대출 조건 입력도 기본 number/select UI를 쓰지 않고 HomeHunt 디자인 시스템의 통화·금리·기간 입력 컴포넌트로 제공한다.

### 분양의 가격 맥락과 지원 흐름

분양 공고 상세는 단순 일정 화면이 아니다.

- 해당 공고의 공식 분양가와 공급 세대, 평형, 신혼 배정 근거를 보여준다.
- 가능하면 같은 단지의 입주 후 실거래 또는 인근 유사 단지의 현재 실거래와 나란히 보여준다.
- `공식 분양가`, `현재 실거래`, `인근 비교 단지 가격`, `자료 없음`을 명확히 분리한다.
- 분양가가 확인되지 않으면 추측하지 않고 원문 확인 링크를 제공한다.
- `청약 신청하기`는 청약홈·LH·SH 등 공식 신청 페이지로 이동시키고, 신청 기간·준비 서류·확인해야 할 자격을 체크리스트로 제공한다.
- 사용자의 본인 인증, 청약 신청서 제출, 주민등록번호·통장번호 입력을 자동화하거나 저장하지 않는다.

# 포털 정보(NAVER 부동산·다방·직방 등) 확장 원칙

사용자가 직접 검색해서 연 단지 상세에 대해, 허용되는 범위 안에서 더 많은 정보를 보강할 수 있으면 좋다. 그러나 이 기능은 법적·약관·기술적 제약을 우회하는 크롤러가 되어서는 안 된다.

## 반드시 지킬 원칙

1. 공식 API, 공식 제휴, 공개적으로 허용된 RSS/데이터, 명시적으로 허용된 웹 접근을 우선한다.
2. 각 제공자의 최신 이용약관, robots 정책, API 문서, 요청 한도를 구현 전에 확인한다.
3. 로그인이 필요하거나 접근 제어를 우회해야 하는 데이터, CAPTCHA 우회, 비공개 API 호출, 대량 수집, 무한 스크롤 전수 수집은 구현하지 않는다.
4. `네이버부동산`, `다방`, `직방`이라는 이름만으로 자동 크롤링 허용이라고 가정하지 않는다.
5. 허용이 불명확하거나 금지된 경우에는 크롤링하지 않고, 공식 단지/매물 페이지로 안전하게 열어 주고 사용자가 직접 확인하도록 한다.
6. 매물 사진, 중개사 개인 연락처, 사용자 게시물 등 개인정보·저작권 위험이 큰 데이터를 복제·저장하지 않는다.

## 허용된 제공자만 연결할 때의 기술 규칙

- 전수 크롤링 금지: 사용자가 단지 상세를 열거나 `상세 정보 새로고침`을 눌렀을 때만 요청한다.
- 요청은 단지 단위로 제한하고, 짧은 시간에 반복 요청하지 않는다.
- 공급자별 rate limit, exponential backoff, 동시성 제한, 24시간 이상 캐시, 수동 새로고침 쿨다운을 둔다.
- 수집 성공 여부, 제공자, 조회 시각, 데이터 범위, 사용한 방식(API/허용된 공개 페이지)을 함께 저장·표시한다.
- 실패 또는 미허용 상태에서는 우회 재시도하지 않고 `연결 불가 / 약관상 미지원 / 공식 페이지에서 확인`으로 표시한다.
- 포털 가격은 `매물 호가·매물 수`이고 국토부 가격은 `실제 계약가`임을 UI에서 계속 구분한다.

## 권장 구현 구조

- `providers/official/`: data.go.kr, K-apt, 청약홈, LH, SH, 지역지수 등 공식 원천
- `providers/portal/`: 제공자별 정책 확인과 허용된 단지 상세 보강 어댑터
- `providers/portal/`은 기본 비활성으로 두고, 제공자별 권한·약관·요청 한도 검증 후에만 활성화한다.
- 모든 후보 상세에는 데이터 출처 배지와 최종 확인 시각을 표시한다.
- 포털 연동이 없더라도 공식 실거래·공식 단지 정보만으로 기능이 완전히 동작해야 한다.

# 데이터·보안 원칙

- `homehunt/.env`는 Git에 절대 넣지 않는다.
- 키·토큰·개인 주소·청약 개인 정보는 화면, 로그, 공개 JSON, 저장소에 넣지 않는다.
- 개인 방문 기록·목적지·청약 프로필은 공개 GitHub 데이터와 분리한다.
- 기존 localStorage, IndexedDB, JSON 백업 계약을 가능한 유지한다.
- GitHub Pages에서는 안전한 동적 API 호출이 제한되므로 Firebase Functions, Cloud Run, 비공개 Firestore로 이전 가능한 구조를 설계한다.
- 네이버부동산 비공식 크롤링을 핵심 데이터 계약으로 사용하지 않는다.
- 호가·매물과 국토부 실거래는 명확하게 분리한다.

# 디자인 톤

- 네이버부동산의 지도 탐색 습관은 참고하되, 디자인을 복제하지 않는다.
- 밝고 신뢰감 있는 부동산 서비스 톤을 만든다.
- 흰색·중립 표면을 기본으로 하고 네이비·블루 계열을 주요 색으로 사용한다.
- 의미 없는 통계 카드, 과한 그라디언트, 장식성 카드 남발, 과도한 그림자는 피한다.
- 데이터 출처, 신선도, 확정·추정·미확인 상태를 일관된 디자인 토큰으로 구분한다.
- 차트와 지도는 장식이 아니라 의사결정에 도움이 되어야 한다.

1. 기존 `homehunt/` 코드, 데이터 계약, 환경변수, 로컬 서버를 먼저 분석한다.
2. 유지할 기능, 제거할 UI 습관, 새 정보구조를 짧게 제안한다.
3. 승인 대기 없이 합리적 판단으로 실제 구현한다.
4. 기존 국토부 조회, 지도, 목적지, 방문 기록, 캐시, 분양 수집, 알림 파이프라인을 더 좋은 구조로 이관한다.
5. 거대한 `js/app.js`는 화면별 controller, service, state, provider 단위로 점진 분리한다.
6. 지도 화면 초기 성능을 우선하고, 분양·예측·상세 보강은 필요 시 지연 로드한다.
7. 데스크톱, 태블릿, 390px/430px 모바일을 실제로 검증한다.
8. 자동 테스트와 실제 브라우저 시나리오를 실행한다.

- 포털 보강 기능의 제공자별 허용 근거·요청 한도·캐시 정책
- 테스트 결과
- 로컬 실행 방법

- 다음 우선순위
