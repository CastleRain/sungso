# HomeHunt 다음 고도화 브리프

> 출발점: `2.5.0-handoff`
>
> 작성일: 2026-09-04
>
> 목적: 현재 구현을 무너뜨리지 않고 다음 개발 라운드의 범위와 완료 기준을 고정한다.

## 1. 제품 목표를 한 문장으로

성우와 소희가 여러 회사로 실제 출근 가능한 서울·경기 아파트와 분양 기회를 지도에서 찾고, 방문 당시부터 현재까지의 가격 변화를 신뢰할 수 있는 근거와 함께 관리하는 개인용 집 탐색 도구다.

## 2. 고도화에서도 바꾸지 않을 핵심 구조

메뉴는 `집 찾기 · 내 기록 · 실거래 · 분양·청약 · 사용 안내 · 연결 상태` 여섯 개를 유지한다. `더보기`에 숨기지 않는다.

- **집 찾기:** 조건에 맞는 미방문 아파트까지 포함한 전체 후보 탐색
- **내 기록:** 실제 방문한 집과 관심 후보를 개인 맥락으로 관리
- **실거래:** 단지와 정확한 전용면적별 계약 가격·추세·예상 근거 확인
- **분양·청약:** 서울·경기 공고, 신혼 관련 공급, 맞춤 조건, 준비도, 알림
- **사용 안내:** 처음 보는 사람에게 기능과 데이터 의미 설명
- **연결 상태:** 사이트 오류와 데이터/API 미연결을 구분

화면 사이에는 반드시 맥락을 유지하는 이동을 둔다.

```text
집 찾기 후보 ──→ 실거래 상세
      │             │
      ├─→ 관심 저장 │
      └─→ 방문 기록 ┘
             │
             └─→ 방문 당시 대비 현재 가격

분양 공고 ──→ 지도 위치 / 관심 공고 / 공식 원문 / 알림
```

## 3. 절대 지켜야 할 데이터 원칙

1. 실거래가, 공고, 경로, 역 거리, 당첨 가능성을 가짜 샘플로 채우지 않는다.
2. 화면의 숫자에는 원천, 기준 시점, 표본 수, 거래 유형, 전용면적 범위를 붙인다.
3. 직선거리로 대중교통 소요시간을 단정하지 않는다.
4. 경로 미확인은 `1시간 이내` 통과로 처리하지 않는다.
5. 예측 품질이 낮으면 숫자를 숨긴다. 보류가 실패보다 안전하다.
6. `당첨 확률`은 검증 가능한 모집군·경쟁률·가점/추첨 자료가 없으면 표시하지 않는다.
7. 방문 기록과 부부 조건은 공개 JSON이나 GitHub 저장소에 넣지 않는다.
8. `.env`의 실제 키 값은 코드, 화면, 로그, 캡처, 문서에 넣지 않는다.
9. 네이버부동산 페이지의 비공식 크롤링을 핵심 데이터 계약으로 삼지 않는다. 공식 API와 사용자가 연 공식 링크를 우선한다.
10. 빈 상태는 빈 상태로 설명한다. `0건`, `승인 대기`, `호출 실패`, `조건 불일치`를 서로 구분한다.

## 5. 현재 한계와 우선순위

## P0 — 다음 라운드에서 먼저 끝낼 것

### P0-1. 실제 분양 데이터 기준선 만들기

현재 UI와 수집 파이프라인은 있으나 캡처 시 공식 공급 피드는 0건이다. 다음 단계의 최우선 과제는 적어도 하나의 공식 원천에서 실제 서울·경기 공고를 안정적으로 받는 것이다.

구현 범위:

- LH 공공데이터 및 SH 공급 데이터 승인·응답 확인
- 청약홈은 제공 가능한 공식 공개 채널을 우선하고 약관을 위반하는 우회 크롤링은 피하기
- 공급원별 `정상 0건`, `승인 대기`, `인증 실패`, `형식 변경`, `일시 장애` 상태 분리
- 공고 ID, 원천 URL, 공고일, 접수기간, 공급유형, 지역, 전용면적, 가격/보증금, 신혼 관련 키워드 정규화
- 첫 성공 수집은 기준선으로 저장하고 전량 신규 알림을 보내지 않기
- 이후 신규·변경·마감임박만 알림 후보로 만들기

완료 기준:

- 공식 원문으로 역추적 가능한 서울·경기 공고가 화면에 표시된다.
- 공급원 하나가 실패해도 다른 공급원 결과는 보인다.
- 0건일 때 이유와 마지막 성공 시각이 화면에 나온다.
- 테스트 픽스처가 실제 응답 필드 계약을 검증한다.

### P0-2. 지도 후보 좌표와 클러스터 완성도

공식 카탈로그는 모든 단지 좌표를 보장하지 않아 첫 화면의 일부 핀은 방향 제시용이다. 실제 조건 결과는 필요한 단지를 지오코딩하면서 보강하지만, 지도에서 결과 누락처럼 보일 수 있다.

구현 범위:

- 서울·경기 17,851개 단지 좌표 사전 보강 ETL
- 주소 정규화와 지오코딩 실패 재시도/수동 교정 목록
- 좌표의 원천과 신뢰도 기록
- 검색 결과 건수, 지도 마커 건수, 좌표 미확인 건수를 별도 표시
- 줌 레벨에 따른 클러스터와 개별 가격 핀 전환 검증
- 아파트·분양·관심·방문 마커의 모양과 범례 일관화

완료 기준:

- 조건 결과 중 좌표 확인된 후보가 모두 지도에 표시된다.
- 지도 숫자와 결과 시트 숫자의 차이를 사용자가 이해할 수 있다.
- 같은 위치의 후보가 클릭 불가능하게 겹치지 않는다.

### P0-3. 화면 문구와 내부 판정 경계 통일

현재 일부 UI는 `6억 미만`이라고 말하지만 코어 판정은 `6억 이하(<=)`다. 이런 경계 불일치는 추천 신뢰를 떨어뜨린다.

구현 범위:

- 최대 가격, 최대 연식, 최대 시간의 `미만/이하` 계약을 제품 전체에서 하나로 통일
- 최소 면적, 최소 세대수의 `초과/이상` 계약 통일
- 폼 레이블, 자연어 파서, 필터 칩, 서버 요청, 코어 비교식, 테스트를 동시에 수정
- 경계값 테스트 추가: 정확히 6억원, 500세대, 20년, 60분, 66.1㎡

완료 기준:

- 화면 설명과 코드 비교 연산자가 동일하다.
- 경계값 자동 테스트가 모두 통과한다.

### P0-4. 모바일 실사용 시각 검수

현재 자동 계약은 있지만 인수인계 캡처는 데스크톱 위주다.

구현 범위:

- 390×844와 430×932에서 여섯 화면 캡처
- 하단 내비와 지도 컨트롤 충돌 제거
- 필터·결과·단지 상세 바텀시트의 단계별 높이 조절
- 모달 키보드 열림, safe area, 가로 넘침, 터치 타깃 점검
- 지도 드래그와 시트 스크롤 제스처 충돌 점검

완료 기준:

- 전 화면에 의도치 않은 가로 스크롤이 없다.
- 첫 화면에서 지도 면적이 필터보다 크다.
- 핵심 행동은 한 손 엄지 범위에서 실행 가능하다.

## P1 — 실제 사용 편의와 정확도를 높일 것

### P1-1. 여러 회사 통근을 비용 제한 안에서 정확하게

TMAP 무료 호출이 하루 10회 수준인 키도 있으므로 모든 후보×모든 목적지를 매번 재호출하면 안 된다.

권장 전략:

1. 가격·면적·세대수·연식으로 후보를 먼저 크게 줄인다.
2. 목적지까지 직선거리로 불가능한 후보를 제외하되, 직선거리만으로 통과시키지는 않는다.
3. 좌표·수단·출발 시각·목적지·옵션을 fingerprint로 만들어 경로 결과를 장기 캐시한다.
4. 동일 조건 재검색은 캐시를 사용한다.
5. NAVER 자동차는 자동차 조건에 사용한다.
6. 대중교통은 Kakao Mobility가 설정되면 우선하고, TMAP은 상위 후보의 정밀 검증 또는 사용자 요청 시 사용한다.
7. 무료 쿼터가 부족하면 `미확인`으로 남기고 사용자가 검증할 후보를 고르게 한다.
8. 장기적으로는 공식 대중교통 경로 또는 유료 플랜의 비용·약관을 확인해 제공자를 교체 가능하게 유지한다.

다중 목적지 점수는 평균만 보지 말고 다음을 함께 표시한다.

- 목적지별 실제 시간
- 가장 긴 통근시간
- 주당 방문일을 반영한 가중 평균
- 둘 사이의 시간 격차
- 모든 필수 목적지 충족 여부

현재 주당 방문일은 목적지별로 저장하지만 이동 수단과 허용 시간은 일부 공통값으로 덮어쓰는 구간이 있다. 목적지마다 수단·허용시간·출발 요일/시간을 독립적으로 저장하도록 확장한다.

완료 기준:

- 같은 검색을 반복해도 외부 호출이 불필요하게 증가하지 않는다.
- 하나라도 필수 목적지가 시간을 초과하면 기본 추천에 나오지 않는다.
- 경로 공급자와 조회 시각이 후보 상세에 표시된다.
- 호출 한도 소진 시에도 캐시 후보와 미확인 상태로 기능이 유지된다.

### P1-2. 역세권을 실제 필터로 만들기

현재 `역 도보 10~20분`은 모든 단지에 대해 검증된 역 좌표·보행 경로가 없어 완전한 하드필터가 아니다.

구현 범위:

- 수도권 역 출입구 좌표 데이터 확보
- 단지 대표 출입구 또는 중심점과 역 출입구 간 보행 경로 계산
- 가장 가까운 역 이름, 노선, 출입구, 거리, 예상 도보시간 저장
- 직선 환산이면 `추정`, 보행 경로면 `확인`으로 구분
- `최소 10분`과 `최대 20분`을 모두 적용할지 제품 의미 확정

완료 기준:

- 역 정보가 없는 후보를 자동 통과시키지 않는다.
- 지도에서 단지–역 연결과 도보시간 근거를 확인할 수 있다.

### P1-3. 관심 후보와 방문 기록 비교 통합

현재 관심 후보와 방문 기록은 개념적으로 분리되어 있으나 비교 기능의 일부는 방문 기록 중심이다.

구현 범위:

- 비교함이 관심 후보와 방문 기록을 모두 받을 수 있게 공통 비교 스냅샷 정의
- `방문함`, `관심만`, `분양` 출처 배지 표시
- 확인되지 않은 필드는 `-`가 아니라 `미확인`과 확인 방법 표시
- 가격, 면적, 연식, 세대수, 교통, 당시 메모, 최근 실거래, 추세를 열 단위로 비교
- 저장 당시와 현재 값의 변화를 별도 행으로 제공

완료 기준:

- 집 찾기 후보 2개와 방문 집 1개를 같은 비교표에서 비교할 수 있다.
- 출처가 다른 가격을 같은 의미의 숫자처럼 섞지 않는다.

### P1-4. 실거래 결과의 인터랙션과 설명 강화

구현 범위:

- 조회 단계별 진행 상태: 단지 찾기 → 월 자료 수집 → 면적 분류 → 차트 계산
- 차트 점 hover/tap에서 계약일·가격·층·면적 표시
- 1년/3년/5년 전환 시 차트, 평균, 거래량, 예상이 동시에 변경
- `평균 가격`, `평당 평균`, `최근 거래`의 차이를 짧은 도움말로 설명
- 현재·직전 신고 진행월의 잠정 데이터 표시
- 조회한 단지·면적·기간을 URL 또는 화면 상태로 복원

완료 기준:

- 느린 조회 중 사용자가 멈춤으로 오해하지 않는다.
- 검색 조건을 바꾸면 화면의 모든 요약이 같은 데이터 범위로 재계산된다.

### P1-5. 실제 휴대폰 알림

가장 빠른 실사용 경로는 Telegram이다. Firebase Cloud Messaging은 앱 설치감과 기기별 권한 관리에 유리하지만, HTTPS 서비스 워커·토큰 저장·인증·백엔드 발송이 필요하다.

권장 단계:

- 1단계: GitHub Actions 또는 안전한 서버 스케줄 + Telegram Bot
- 2단계: Firebase Authentication 도입 후 사용자별 조건을 비공개 Firestore에 저장
- 3단계: FCM 웹 푸시 또는 설치형 PWA 알림

알림은 `신규`, `조건 변경`, `접수 3일 전`, `오늘 마감`을 구분하고 동일 공고·동일 이벤트 중복을 ledger로 막는다.

완료 기준:

- 최초 기준선 수집 때 대량 알림이 오지 않는다.
- 같은 공고 알림이 중복되지 않는다.
- 공식 원문, 접수기간, 매칭 이유가 알림에 포함된다.
- 사용자가 즉시 전체 또는 조건별 알림을 끌 수 있다.

## P2 — 장기 고도화

### P2-1. 가격 예측 고도화

현재 예측은 해당 실거래 시계열 중심이다. 다음 요인을 추가하더라도 단일 `정답 가격`처럼 보이지 않게 해야 한다.

후보 변수:

- 같은 단지·같은 면적의 거래량과 층/동 편차
- 인근 단지의 동일 평형 흐름
- 한국부동산원 지역 매매가격지수
- 금리와 대출 규제의 시점 변수
- 입주 물량과 분양 공급
- 역세권, 연식, 세대수 등 단지 특성

권장 출력:

- 6개월 후 평균 예상 범위
- 상승/보합/하락 방향 확률이 아니라 시나리오 구간
- 과거 롤링 백테스트 오차
- 예측에 가장 영향을 준 근거 3개
- 자료 부족/구조 변화 경고

완료 기준:

- 미래 정보를 학습에 섞지 않는 시간 순서 검증을 유지한다.
- 단순 최근값 기준보다 검증 오차가 실제로 개선된 경우에만 새 모델을 채택한다.
- 오차가 큰 단지는 계속 보류한다.

### P2-2. 부부 전용 동기화

GitHub에 DB 파일을 올리면 공개 저장소에서 개인정보가 노출되고 동시 수정 충돌도 생긴다. 최종 배포는 파일 DB가 아니라 인증된 백엔드가 맞다.

권장 구조:

- Firebase Authentication: 두 사람 계정 또는 초대 코드
- Firestore: 방문 기록, 관심 후보, 목적지, 조건, 알림 설정
- Security Rules: 부부 공유 household ID만 읽기/쓰기
- 공개 정적 파일: 카탈로그와 비개인 집계만
- 비밀키 호출: Firebase Functions/Cloud Run 또는 별도 API
- 오프라인: IndexedDB 캐시와 재연결 동기화

완료 기준:

- 다른 브라우저에서도 두 사람 기록이 동기화된다.
- 로그인하지 않은 사용자는 개인 기록을 읽을 수 없다.
- 외부 API 서버키는 브라우저 번들에 포함되지 않는다.

### P2-3. 프런트 구조 분리와 성능

`homehunt/js/app.js`는 화면 오케스트레이션이 한 파일에 집중되어 있다.

권장 분리:

```text
js/
├─ app-shell/
│  ├─ navigation.js
│  ├─ router.js
│  └─ state.js
├─ features/
│  ├─ finder/
│  ├─ records/
│  ├─ market/
│  ├─ supply/
│  ├─ guide/
│  └─ connections/
├─ services/
│  ├─ local-api.js
│  ├─ map.js
│  └─ storage.js
└─ core/               기존 순수 .mjs 모듈 유지
```

한 번에 전체를 다시 쓰지 말고 화면별 컨트롤러를 하나씩 추출한다. 기존 순수 코어 테스트를 안전망으로 유지한다.

완료 기준:

- 화면별 상태와 DOM 이벤트 소유권이 명확하다.
- 초기 지도 화면에 필요하지 않은 분양/예측 코드는 지연 로드된다.
- 기존 URL, 저장 키, API 계약이 마이그레이션 없이 깨지지 않는다.

## 6. 상세 UX 개선 기준

### 집 찾기

- 기본 상태에서 지도는 데스크톱 가용 높이의 대부분을 사용한다.
- 필터는 한 행의 칩과 슬라이더 프리셋을 우선하고 고급 입력은 접는다.
- 클러스터를 클릭하면 자연스럽게 확대하고 해당 범위 결과 수를 갱신한다.
- 지도 이동 후 `이 지역 다시 검색`을 제공한다.
- 마커 선택과 결과 카드 선택은 양방향으로 동기화한다.
- 방문 집은 별표/방문 배지를 겹쳐 표시하되 일반 후보를 숨기지 않는다.
- 분양 레이어를 켜면 기존 아파트와 다른 마커로 같은 지도에 표시한다.

### 내 기록

- 목록/지도/비교를 같은 데이터 범위의 세 보기로 취급한다.
- 방문 당시 스냅샷은 이후 실거래 업데이트로 덮어쓰지 않는다.
- 현재 가격 변화는 별도 계산값으로 표시한다.
- 성우/소희 평가는 둘 다 보이되 점수 평균 하나로 맥락을 지우지 않는다.

### 실거래

- 첫 화면에는 단지명, 면적, 기간, 평균 가격, 변화 방향, 거래량, 차트를 우선한다.
- 복잡한 모델 진단은 `예상 근거` 하위 패널로 이동한다.
- 한 화면에 들어가지 않는 최근 개별 거래는 별도 상세 목록으로 연다.
- `평당 가격`은 보조 비교값이고 실제 계약 가격이 주 정보다.

### 분양·청약

- 기본 목록은 접수 중/예정과 내 조건 매칭을 우선한다.
- 공고 카드에서 공급 유형, 지역, 전용면적, 가격, 접수기간, 매칭 이유가 한눈에 보여야 한다.
- 자격 판정은 `가능`, `불가`, `확인 필요`로 나누고 근거 조항 또는 공식 원문 위치를 제공한다.
- 관심 공고와 알림 상태를 같은 카드에서 조작한다.

## 7. 테스트와 검증 전략

### 자동 테스트

- 모든 순수 코어 모듈 단위 테스트
- 추천 경계값과 누락 월 배제
- 다중 목적지 전체 충족/부분 초과/전부 미확인
- 경로 캐시 fingerprint와 호출 한도
- 실거래 1/3/5년 및 면적 전환
- 예측 공개/보류 게이트
- 공급원별 실패 격리, 기준선, 신규/변경 판정
- 알림 중복 방지
- 6개 메뉴·가이드·분양 UI 계약
- 저장 데이터 이전 호환성

### 실제 브라우저 시나리오

1. 새 브라우저 상태에서 모든 빈 화면 확인
2. 회사 2곳을 장소 검색으로 저장
3. `6억 이하 · 20평 이상 · 500세대 이상 · 20년 이하 · 통근 60분 이하` 검색
4. 검색 진행 상태와 결과/지도 숫자 확인
5. 후보 하나를 관심 저장하고 실거래로 이동
6. 기간과 전용면적 변경 후 모든 숫자 동시 갱신 확인
7. 방문 기록 저장 후 내 기록 지도와 당시 대비 가격 확인
8. 분양 조건 저장, 공식 피드/빈 상태/관심/알림 확인
9. API 하나를 의도적으로 끄고 연결 상태와 기능 저하 확인
10. 1146px, 768px, 430px, 390px에서 화면 캡처와 콘솔 오류 확인

### 성능 기준

- 지도 첫 상호작용은 대형 카탈로그 파싱에 막히지 않아야 한다.
- 지도 이동 시 전체 마커를 매번 새로 만들지 않는다.
- 동일 실거래 월과 경로는 캐시를 재사용한다.
- 느린 검색 요청은 새 요청이 시작되면 결과 반영을 중단한다.

구현 전 현재 페이지를 직접 사용해 기준 화면과 콘솔을 기록하고, 구현 후 같은 시나리오로 비교해. 기존 자동 테스트 전체와 새 경계값 테스트를 통과시키고, 1146px/430px/390px 캡처를 남겨. 화면만 꾸미지 말고 검색 조건을 바꿀 때 지도·카드·차트·요약 숫자가 같은 상태로 실제 갱신되는지 확인해.

## 9. 완료 정의

다음 라운드는 코드가 실행된다는 이유만으로 완료하지 않는다.

- [ ] 조건을 바꾸면 지도, 목록, 요약이 모두 같은 검색 상태로 갱신된다.

- [ ] 관심 후보와 방문 기록의 의미가 섞이지 않는다.
- [ ] 단지와 전용면적을 바꾸면 실거래 전체 화면이 재계산된다.
- [ ] 평균/평당/최근 가격의 의미가 화면 안에서 이해된다.
- [ ] 예측 보류가 정상 상태로 설명된다.
- [ ] 공식 분양 공고가 원문 링크·원천·시점과 함께 보인다.
- [ ] 신혼 조건 매칭과 신청 준비도가 근거와 함께 보인다.
- [ ] 모바일 알림은 중복 없이 끌 수 있다.
- [ ] 개인정보와 서버키가 공개 정적 자산에 없다.
- [ ] 데스크톱·태블릿·모바일에서 콘솔 오류와 가로 넘침이 없다.
- [ ] 자동 테스트와 실제 브라우저 시나리오가 모두 통과한다.
- [ ] 새 캡처, 변경 로그, 다음 한계를 인수인계 문서에 갱신한다.
