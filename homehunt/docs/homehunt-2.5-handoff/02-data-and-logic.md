# HomeHunt 2.5 데이터와 동작 원리

> 기준 버전: HomeHunt 화면·로컬 API `2.5.0`
>
> 기준일: 2026-09-04
>
> 목적: 다음 개발자가 화면의 숫자를 어디서 가져오고, 어떤 조건으로 후보를 남기며, 무엇을 아직 믿으면 안 되는지 코드까지 추적할 수 있게 하는 인수인계 문서

## 1. 먼저 알아야 할 제품 원칙

HomeHunt는 현재 매물 호가를 보여주는 네이버 부동산 복제 서비스가 아니다. 다음 세 종류의 정보를 의도적으로 분리한다.

1. **공식 공개 정보**: 한국부동산원 공동주택 단지 목록, 국토교통부 아파트 매매·전월세 실거래, 청약홈·LH·SH 분양 공고
2. **외부 지도·경로 결과**: NAVER 지도/주소/자동차 경로, NAVER API HUB 장소 검색, Kakao 또는 TMAP 대중교통 경로
3. **두 사람의 개인 기록**: 방문한 집, 현장에서 확인한 가격과 메모, 회사·주요 목적지, 관심 후보, 청약 자가입력

공식 거래와 개인이 현장에서 들은 호가는 서로 섞지 않는다. 회사 좌표와 방문 메모도 공개 데이터 파일에 넣지 않는다. 검색 결과가 부족하더라도 임의의 단지나 가격을 실제 데이터처럼 생성하지 않는다.

현재 코드의 핵심 진입점은 다음과 같다.

- 화면 상태·흐름: [`js/app.js`](../../js/app.js)
- 브라우저 저장: [`js/storage.js`](../../js/storage.js)
- 단지/거래 계산: [`js/recommendation-core.mjs`](../../js/recommendation-core.mjs), [`js/market-core.mjs`](../../js/market-core.mjs)
- 다중 통근: [`js/commute-balance-core.mjs`](../../js/commute-balance-core.mjs), [`js/recommendation-verification-core.mjs`](../../js/recommendation-verification-core.mjs)
- 로컬 중계 서버: [`scripts/local-market-server.mjs`](../../scripts/local-market-server.mjs)
- 분양 수집·알림: [`scripts/fetch-home-supply.mjs`](../../scripts/fetch-home-supply.mjs), [`scripts/send-supply-telegram.mjs`](../../scripts/send-supply-telegram.mjs)

## 2. 전체 구조

HomeHunt는 빌드가 필요한 프레임워크 앱이 아니라 HTML/CSS/JavaScript 정적 앱이다. 다만 비밀키가 필요한 실거래·장소·경로 기능은 브라우저에서 직접 호출하지 않고 로컬 Node 서버 또는 예약 작업에서 처리한다.

```text
┌──────────────────────────────── 브라우저 ────────────────────────────────┐
│ index.html + app.js                                                     │
│  ├─ 공식 단지/법정동/공개 집계/분양 JSON 읽기                           │
│  ├─ NAVER Maps Web SDK로 지도·주소 변환                                 │
│  ├─ localStorage: 방문·목적지·관심·분양조건·청약 자가입력                │
│  └─ IndexedDB: 가져온 CSV 집계·완전한 단지 실거래 이력                   │
└───────────────────────┬──────────────────────────────────────────────────┘
                        │ localhost에서만 HTTP
┌───────────────────────▼──────── HomeHunt 로컬 API :8787 ────────────────┐
│ 국토부 월별 실거래 / 단지 이력 / 추천 작업 / 장소 검색 / 통근 행렬      │
│ 키는 환경변수·.env 또는 서버 메모리에만 보관                            │
│ .local/: 월·단지·분양 파일 캐시와 Kakao/TMAP 사용량 장부                 │
└──────────────┬───────────────────────────────┬───────────────────────────┘
               │                               │
       공식 공공데이터 API              NAVER/Kakao/TMAP API

┌──────────────────────────── GitHub Actions ─────────────────────────────┐
│ 국토부 지역 집계 → market-summary.json / apartment-history.json         │
│ 청약홈·LH·SH 수집 → home-supply.json → 조건 필터 → Telegram             │
└──────────────────────────────┬───────────────────────────────────────────┘
                               ▼
                         GitHub Pages 정적 배포
```

이 구조에서 **GitHub Pages 배포본과 로컬 실행본의 기능 범위가 다르다.** 배포본은 공개 정적 JSON을 읽을 수 있지만, 현재 `config.js`는 맞춤 추천·통근·장소 검색을 localhost API에만 연결한다. 배포 환경의 단지 이력 Firebase Function URL은 준비돼 있으나 `apartmentHistoryEnabled`가 로컬 환경에서만 참이므로, 현재 배포본에서는 주문형 단지 이력을 호출하지 않는다.

## 3. 데이터 출처와 현재 상태

### 3.1 데이터 출처 표

| 데이터 | 실제 출처 | 현재 쓰임 | 코드/파일 | 신뢰 경계 |
|---|---|---|---|---|
| 서울·경기 아파트 기본 목록 | 한국부동산원 전국 공동주택 단지정보 CSV | 단지명·주소·법정동·세대수·사용승인연도 기반 검색과 1차 추천 | `data/apartment-catalog-seoul-gyeonggi.json` | 거래가격이나 현재 매물이 아님 |
| 법정동/시군구 코드 | 공식 법정동 자료로 만든 정적 대조표 | 주소와 5자리 시군구 코드를 연결 | `data/law-districts.json` | 원본 갱신 뒤 재생성이 필요함 |
| 매매 실거래 | 국토교통부 아파트 매매 실거래가 API | 단지 이력, 추천 예산 판정, 지역 집계 | localhost API, Actions | 신고 취소·정정 및 최근월 지연 가능 |
| 전월세 실거래 | 국토교통부 아파트 전월세 실거래가 API | 단지별 전세/월세 이력 | localhost API, Actions | 월세는 보증금과 월세가 분리되며 단일 매매가로 환산하지 않음 |
| 지역 월별 집계 | 위 국토부 자료를 Actions 또는 CSV 가져오기로 재집계 | 지역·면적대 가격 흐름 | `data/market-summary.json`, IndexedDB | 현재 저장소의 정적 파일은 아직 `empty` 상태일 수 있음 |
| 계속 추적할 단지 | 사용자가 공개 설정에 명시한 단지 | 예약 수집 단지 이력 | `config/tracked-apartments.json`, `data/apartment-history.json` | 개인 메모를 넣는 파일이 아님 |
| 분양 공고 | 청약홈 APT/잔여/임의공급, LH 분양/신혼희망타운, SH 공식 RSS | 분양 목록·일정·조건 필터·알림 | `data/home-supply.json` | 공급원별 승인과 필드 제공 여부가 다름 |
| 지도/주소 | NAVER Maps Web SDK | 지도, 주소 검색, 역지오코딩, 좌표 확정 | `js/naver-map.js` | 상호/회사명 POI 검색 API가 아님 |
| 회사/건물명 | NAVER API HUB 지역 검색 + Kakao 우편번호 주소 DB 보조 | 회사·건물 후보 검색 | localhost `/api/place-search`, 브라우저 주소 모달 | 주소 DB는 입점 상호를 모두 보장하지 않음 |
| 자동차 경로 | NAVER Directions 5 | 후보→목적지 자동차 시간 | localhost `/api/commute*` | 실시간 상황과 호출 시점에 따라 달라짐 |
| 대중교통 경로 | Kakao 대중교통 또는 TMAP 대중교통 | 광역 선별과 최종 통근 검증 | localhost `/api/commute*` | Kakao 결과에는 현재 구현상 출발시각 파라미터가 없음 |
| 개인 방문·조건 | 사용자의 브라우저 입력 | 내 기록, 관심 후보, 목적지, 분양/청약 조건 | localStorage | 기기·브라우저별 데이터이며 자동 공유되지 않음 |

### 3.2 공식 단지 카탈로그

현재 서울·경기 카탈로그 메타데이터에는 다음 계보가 기록되어 있다.

- 원본: 한국부동산원 전국 공동주택 단지정보 CSV
- 정적 필터: `단지종류=1`
- 전국 아파트 45,920개에서 서울·경기 17,851개 추출
- 지역 판정 보조: `law-districts.json`
- 원본 게시일·원본 행 수·SHA-256이 `data/apartment-catalog-seoul-gyeonggi-meta.json`에 기록됨

따라서 “17,851개”는 현재 가격이 있는 매물 수가 아니라 **검색 가능한 공식 아파트 단지 기준선의 수**다. 세대수·준공연도 같은 카탈로그 필드가 비어 있으면 추천 하드 조건을 통과하지 못할 수 있다.

### 3.3 지금 저장소에 커밋된 공개 데이터 상태

문서 작성 시점의 공개 파일은 다음 상태다.

- `market-summary.json`: `sourceType: empty`, 지역 집계 없음
- `home-supply.json`: `awaiting_api_access`, 공고 0건, 공급원별 첫 정상 기준선 미수립
- 공식 단지 카탈로그: 서울·경기 17,851개 존재

즉, **기능 코드가 구현돼 있다는 것과 현재 공개 JSON에 실제 데이터가 채워져 있다는 것은 다르다.** 로컬 `.env` 또는 Actions Secrets의 키 값은 이 문서를 만들 때 확인하지 않았으며, 연결 여부는 화면의 `연결 상태` 또는 localhost `/api/health`에서 값이 아닌 상태 플래그로 확인해야 한다.

## 4. 저장 위치와 데이터 수명

### 4.1 브라우저 localStorage

| 키 | 저장 내용 | 최대/정리 규칙 |
|---|---|---|
| `homehunt_visits_v1` | 실제 방문 기록, 주소·좌표·현장 가격·평가·메모 | 전체 배열 |
| `homehunt_compare_ids_v1` | 비교할 방문 ID | 유효 방문만 정리, 비교는 최대 3개 |
| `homehunt_recent_complexes_v1` | 최근 검색한 단지 문맥 | 최신 12개 |
| `homehunt_shortlist_v1` | 관심 후보와 저장 당시 가격/통근 판정 문맥 | 화면에서 최대 60개 |
| `homehunt_recommendation_filters_v1` | 지역·가격·면적·연식·역 도보·통근 조건과 목적지 A–D | 마지막 조건 1세트 |
| `homehunt_geocode_cache_v1` | 주소/이름→좌표·도로명/지번 변환 결과 | 최신 400개 |
| `homehunt_supply_preferences_v1` | 분양 지역·동네·가격·면적·세대수·미공개 포함·알림 조건 | 마지막 조건 1세트 |
| `homehunt_supply_favorites_v1` | 관심 분양 공고 ID | 최대 500개 |
| `homehunt_supply_seen_v1` | 분양 기준선·읽지 않음·알림 중복 키 | 각 목록 최근 2,000개 |
| `homehunt_subscription_profile_v1` | 성우·소희 청약 자가입력 | 마지막 프로필 1세트 |

방문 기록의 현재 계약은 대략 다음과 같다.

```js
{
  id, name, address, lat, lng, visitDate,
  dealType, askingPrice, areaM2, floor, builtYear,
  households, walkMinutes, direction, status,
  visitedBy: ['성우', '소희'], pros, cons, memo, tags
}
```

`기록 내보내기/백업`은 JSON v2로 `visits`와 `compareIds`를 저장한다. **관심 후보, 회사 목적지, 분양 조건, 청약 프로필까지 전부 백업하는 기능은 아니다.** JSON을 GitHub에 커밋하면 방문 주소와 메모가 공개될 수 있으므로 개인 백업 파일을 저장소에 올리면 안 된다.

localStorage는 같은 브라우저 프로필·같은 사이트 출처에서만 보인다. PC에서 저장한 기록이 휴대폰으로 자동 복제되지 않고, 브라우저 저장소 삭제·시크릿 모드·도메인 변경 시 사라질 수 있다.

### 4.2 브라우저 IndexedDB

DB 이름은 `homehunt_market_v1`, 객체 저장소는 `datasets`다.

- `imported-summary`: 사용자가 가져온 국토부 CSV의 지역·면적대 집계
- `complex:...`: 지역코드, 단지명, `aptSeq`, 법정동, 조회 개월 수, 기준월을 포함한 단지 이력 캐시

단지 이력은 `partial: false`, 요청 개월 수·기준월·시작월·종료월이 모두 맞고 `includesCurrentMonth`가 명시된 **완전한 응답만** IndexedDB에 쓴다. 일부 월만 받은 결과가 이전 완전 캐시를 덮어쓰는 것을 막는다.

### 4.3 로컬 서버 파일 캐시

Git에서 제외된 `homehunt/.local/` 아래에 저장한다.

- `market-cache/months/`: 시군구×월×거래유형 국토부 응답
- `market-cache/history/`: 단지 이력 완전 응답
- `market-cache/home-supply.json`: 로컬에서 갱신한 분양 스냅샷
- `kakao-transit-usage.json`, `tmap-transit-usage.json`: KST 날짜별 보수적 호출 사용량

월 자료 TTL은 현재월 30분, 직전월 12시간, 더 오래된 월 30일이다. 단지 이력은 현재월 포함 시 30분, 과거 기준 범위는 6시간이다. 분양 로컬 파일은 3시간, 실패 후 재시도 대기는 15분이다. 대중교통 경로 캐시는 기본 8시간 메모리 전용, 자동차는 20분 메모리 전용, 장소 검색은 5분 메모리 전용이므로 서버를 재시작하면 이 세 메모리 캐시는 사라진다.

사용량 장부는 실제 Kakao/TMAP 콘솔 사용량의 복사본이 아니다. 이 로컬 서버에서 캐시 미스로 나간 호출만 세므로 다른 앱·기기에서 쓴 양은 공급자 콘솔에서 별도로 확인해야 한다.

### 4.4 공개 저장소와 Firebase

공개 Git 파일에는 공식 데이터와 공개 집계만 둔다.

- `data/market-summary.json`
- `data/apartment-history.json`
- `data/home-supply.json`
- `data/supply-alert-ledger.json` — 전송된 공고의 해시 장부이며 Telegram 토큰이나 개인 주소가 아님

Firebase Function용 단지·월 캐시 컬렉션 설계가 존재하지만, 현재 공개 Pages 화면의 주문형 단지 조회는 꺼져 있다. 기존 프로젝트의 일부 Firestore 컬렉션은 공개 규칙과의 호환성을 유지하고 있으므로 방문기록·회사주소·FCM 토큰 같은 민감정보를 넣지 않는다. 화면의 4자리 PIN은 Firebase 인증이 아니다.

## 5. 아파트 검색과 단지 식별

### 5.1 자유검색

브라우저는 로드한 서울·경기 카탈로그를 직접 검색한다. 검색어는 Unicode NFKC 정규화, 소문자 변환, 공백·기호 제거, 일반어 `아파트` 제거를 거친다. 사용자가 자주 틀리는 `레미안`은 `래미안` 별칭으로 보정한다.

후보 순서는 다음 일치 등급을 절대 우선한다.

1. 공식 단지명 또는 별칭과 정확히 일치
2. 앞부분 일치
3. 포함 일치
4. 지역·동·주소까지 포함한 모든 토큰 일치
5. 제한된 편집거리 기반 오타 유사 일치

검색 핵심 함수 자체는 어느 지역 카탈로그에서도 동작하지만, 현재 `config.js`가 불러오는 제품 데이터는 서울·경기 17,851개다. 기본 검색 결과는 20개, 내부 상한은 50개다. 선택한 단지와 같은 지역 또는 같은 브랜드의 관련 단지도 최대 8개 찾는다.

### 5.2 동명 단지를 섞지 않는 방법

국토부 거래와 카탈로그 단지를 연결할 때 `지역코드 + 법정동 + 정규화 단지명`을 먼저 쓴다. 여러 단지가 남으면 다음 순서로 단 하나가 확정되는 경우에만 연결한다.

1. 별칭이 아니라 주 단지명 정확 일치
2. 주소 끝의 지번 일치
3. 건축연도 정확 일치
4. 건축연도 ±1년 후보가 하나뿐

끝까지 여러 개면 자동으로 하나를 고르지 않는다. 단지 이력 API도 같은 이름이 여러 곳이면 HTTP 409와 후보 목록을 반환해 사용자가 다시 선택하게 한다. `aptSeq`가 있으면 가장 강한 공식 식별자로 사용한다.

### 5.3 회사 검색은 아파트 검색과 분리

회사 목적지는 다음 두 검색을 병렬로 실행한다.

- NAVER Maps Geocoder의 주소 검색
- localhost를 통한 NAVER API HUB 지역 검색의 회사·건물·상호 후보

둘 다 결과가 없으면 Kakao 우편번호 주소 DB를 모달에 열고, 사용자가 고른 도로명/지번을 다시 NAVER 지도 좌표로 확인한다. 마지막 수단은 지도 직접 클릭이다.

현재 회사 검색 호출에서는 아파트 카탈로그 보조검색을 허용하지 않는다. 따라서 `KT`를 아파트 이름 일부와 우연히 맞춰 회사 위치로 쓰는 일이 없다. 회사명 검색 키가 없거나 입점 상호가 주소 DB에 없으면 동네·지점명을 더 붙이거나 지도에서 직접 좌표를 정해야 한다.

## 6. 집 찾기 추천 파이프라인

### 6.1 한눈에 보는 순서

```text
자연어 또는 상세 필터
  ↓ 입력값 정규화·필수값 검사
서울·경기 공식 단지 1차 필터
  - 지역
  - 세대수
  - 준공연도
  ↓ 후보가 있는 시군구×최근 1~6개월 매매 API 작업 생성
월별 응답 완전성 검사 + 실패 요청 저속 재시도
  ↓ 한 달이라도 불완전한 시군구 전체 제외
실거래 ↔ 공식 단지 보수적 식별
  ↓ 전용면적 조건 + 동일 0.1㎡별 산술평균 가격 조건
가격·기본조건 후보 완성
  ↓ 주소 지오코딩(후보 600개 이하일 때)
직선거리 기반 호출 순서/지도 배치
  ↓ 사용자가 "정밀 통근" 실행
Kakao 넓은 선별 → TMAP 소수 최종 검증, 자동차는 NAVER
  ↓ 모든 필수 목적지 시간 충족 후보만 최종 통근 충족
```

### 6.2 자연어 조건 해석

`parseRecommendationQuery()`는 다음 표현을 읽는다.

- 서울/경기/수도권
- `500세대 이상`, `500세대 초과`
- `6억 미만`, `6억 이하`
- `전용 20평 이상` 등 평→㎡ 변환
- `20년 이내`
- `역 도보 10~20분`
- `회사 60분 이내`, 자동차/대중교통

자연어 해석은 입력칸을 채우는 보조 기능이다. 사용자가 상세 숫자를 확인한 뒤 실행해야 한다. 공급면적은 국토부 전용면적 거래와 직접 비교할 수 없으므로 서버 추천에서 거부하고 전용면적만 허용한다.

### 6.3 1차 카탈로그 필터

1차 필터는 지역, 세대수, 최소 준공연도만 적용한다. 가격과 면적은 카탈로그 메타가 아니라 실제 거래로 판단하기 위해 다음 단계로 미룬다.

현재 역 도보 최소/최대값은 입력·자연어 해석·저장까지 구현돼 있지만, 역 좌표나 도보 경로 데이터와 연결되어 있지 않다. **따라서 역 도보 조건은 현재 추천 하드 필터가 아니다.** 이 조건을 충족했다고 화면이나 후속 고도화가 단정해서는 안 된다.

### 6.4 비동기 실거래 작업

브라우저는 `POST /api/recommendations`로 작업을 만들고, 반환된 작업 ID를 약 0.9초 간격으로 조회한다. 서버는 1차 후보가 존재하는 시군구와 선택 기간 1~6개월의 매매 자료를 조회한다.

- 정상 동시성: 4
- 실패 재시도 동시성: 2
- 외부 요청 시작 간격: 최소 300ms
- 실패 재시도 전 대기: 2.5초
- 작업 보존: 마지막 갱신 후 약 1시간
- 사용자는 `DELETE /api/recommendations/{id}`로 취소 가능

월 응답은 요청 지역·월·거래유형이 정확히 맞고, `records` 배열이 있으며, `partial`, 경고, 누락 요청이 없어야 완전한 것으로 본다. 재시도 뒤에도 한 달이 실패한 시군구는 성공한 달만 이용해 가격이 있는 것처럼 보이지 않도록 **그 시군구의 후보와 거래 전체를 해당 실행에서 제외**한다. 제외된 지역·후보·거래 수는 결과 메타에 남긴다.

### 6.5 면적과 가격 판정

추천은 현재 **매매 실거래만** 사용한다. 거래 취소·해제는 정규화 단계에서 버린다.

1. 조건을 통과한 공식 단지와 실거래를 보수적으로 연결한다.
2. 최소 전용면적 조건을 적용한다.
3. 실제 전용면적을 0.1㎡ 단위로 그룹화한다.
4. 각 면적의 조회 기간 거래금액 산술평균을 계산한다.
5. 평균가격이 최대 예산 미만/이하인 면적이 하나라도 있는 단지만 남긴다.
6. 조건을 만족한 면적 중 평균가격이 가장 낮고, 동률이면 거래 수가 많은 면적을 대표 면적으로 선택한다.

후보에는 면적별 평균·중앙값·최근가격·최저·최고·건수도 남지만, 현재 사용자 대표값은 산술평균이다. 서버 결과 문구도 “현재 호가가 아닌 조회 기간 동일 전용면적 실제 거래 평균”임을 명시한다.

### 6.6 지오코딩과 결과 규모 제한

가격 후보가 완성된 뒤에 주소를 좌표로 바꾼다. 저장된 지오코딩 캐시가 있으면 재사용하고, 없으면 NAVER 주소 검색을 쓴다. 목적지별 Haversine 직선거리, 주당 방문일 가중 평균 거리, 가장 먼 목적지 직선거리를 계산해 실제 경로를 호출할 순서를 정한다.

가격 후보가 600개를 넘으면 전체 주소 지오코딩과 지도 표시를 중단하고 조건을 좁히라고 안내한다. 이것은 가격 결과를 가짜로 자르는 것이 아니라 과도한 주소 호출과 읽기 어려운 지도를 막는 안전장치다. 검색 전 지도에 보이는 공식 단지 12개는 방향을 잡기 위한 기준점이며, 가격·면적 조건을 통과한 결과가 아니다.

## 7. 회사 A–D와 통근 판정

### 7.1 현재 입력 계약

목적지는 최대 4개이며 A–D로 표시된다. 각 목적지는 다음 값을 가진다.

- ID, 이름, 주소, 위도·경도
- 필수 목적지 여부(코어 지원, 현재 화면에서 추가한 목적지는 사실상 모두 필수)
- 주당 방문일/가중치
- 허용 교통수단
- 최대 시간
- 출발시각

다만 현재 UI는 **주당 방문일은 목적지별로 입력하지만, 교통수단·최대 통근시간·출발시각은 상단 공통 조건을 모든 목적지에 덮어쓴다.** 코어 계산 함수는 목적지별 값을 받을 수 있으므로 후속 고도화에서 UI만 확장하면 된다.

목적지 좌표가 하나라도 없으면 통근 조건이 있는 추천을 시작하지 않는다. 목적지 변경 시 좌표·교통수단·시간·출발시각·가중치를 정규화한 fingerprint가 바뀌며, 저장 후보의 이전 통근 판정은 삭제하지 않고 `stale/pending`으로 내려 다시 검증하도록 한다. 단순 이름 변경은 좌표가 같으면 fingerprint를 바꾸지 않는다.

### 7.2 직선거리와 실제 통근의 역할

직선거리는 다음에만 사용한다.

- 어떤 후보를 먼저 지오코딩·경로 확인할지 정렬
- 여러 목적지의 넓은 공간적 균형을 보는 프록시
- 실제 경로가 아직 없는 후보를 `미확인` 상태로 정렬

직선거리에서 지하철·버스 시간을 환산하지 않는다. 실제 경로가 없으면 시간 조건을 통과한 것으로 처리하지 않는다.

### 7.3 경로 공급자

| 모드 | 공급자 | 현재 역할 | 주요 반환값 |
|---|---|---|---|
| 대중교통 | Kakao | 많은 후보의 1차 광역 선별 | 시간, 거리, 도보, 환승, 요금, 경로 수 |
| 대중교통 | TMAP | 출발시각 `searchDttm`을 반영한 소수 최종 검증 | 시간, 거리, 도보, 환승, 요금, 경로 유형 |
| 자동차 | NAVER Directions 5 | 자동차 선택 후보의 실제 경로 | 시간, 거리, 통행료, 택시비, 유류비 |

`TRANSIT_PROVIDER=auto`는 Kakao 키가 있으면 Kakao를, 없으면 TMAP을 기본 대중교통 공급자로 고른다. Kakao와 TMAP이 모두 있으면 현재 브라우저 흐름은 다음과 같다.

1. 직선거리상 분산도 고려해 최대 50개 후보를 고른다.
2. Kakao로 각 후보×목적지 행렬을 1차 확인한다.
3. Kakao 결과를 통근 판정, 최악 비율, 평균시간 순으로 정렬한다.
4. TMAP 일일 잔량에서 2회를 예비로 남긴 범위 안에서 최대 2개 후보를 최종 확인한다.

목적지가 여러 개면 후보 하나가 목적지 수만큼 대중교통 호출을 요구한다. 그래서 “최대 2개 후보”도 남은 호출량에 따라 0~2개로 줄어든다. 개별 후보 확인은 TMAP이 연결돼 있으면 해당 후보 하나를 TMAP으로 최종 검증한다.

Kakao API 요청에는 현재 구현상 출발시각 파라미터가 없고 결과에 `provider-default-no-departure-parameter`를 남긴다. 따라서 Kakao 선별을 평일 08:00 최종 결과처럼 표현하면 안 된다. TMAP 최종 결과에만 계산한 다음 평일 출발시각이 들어간다.

### 7.4 배치·쿼터·캐시

서버의 배치 요청은 출발지 1~10개, 도착지 1~4개를 받으며 브라우저가 큰 선별 집합을 여러 번 나눈다. 중복 좌표쌍은 한 번만 요청한다. 실제 공급자 호출 전에 캐시 미스 수를 계산하고 다음 둘 중 하나를 넘으면 외부 요청을 하나도 보내지 않고 전체 배치를 거부한다.

- 요청이 선언한 원호출 안전 상한: 0~40
- 해당 공급자의 KST 일일 로컬 잔량

기본 로컬 정책은 Kakao 1,000회/일, TMAP 10회/일이며 환경변수로 조정할 수 있다. 실제 요금제나 약관 한도를 우회하는 기능이 아니고, 다중 키 회전도 구현하지 않는다.

대중교통 캐시 키에는 공급자·출발/도착 좌표가 들어간다. TMAP에는 출발시각도 들어가고 Kakao에는 들어가지 않는다. 캐시 히트는 로컬 장부를 차감하지 않으며, 캐시 미스 직전에 장부를 예약한다.

### 7.5 모든 목적지 충족과 균형 점수

각 목적지에서 허용 모드 중 시간이 가장 짧은 **검증된** 경로를 고른다. 모든 필수 목적지에 검증된 경로가 있고 각자의 최대시간 안이어야 `matched`다.

- 경로는 모두 있지만 하나라도 시간 초과: `excluded`
- 필수 경로 하나라도 미확인: `pending`

현재 코어의 경계 비교는 `durationMinutes <= maxMinutes`다. 화면 일부 문구는 “60분 미만”이라고 쓰므로 정확히 60분 결과의 문구와 코드가 어긋날 수 있다. 다음 고도화에서는 `이하`로 문구를 통일하거나 비교식을 `<`로 바꿔 계약을 하나로 맞춰야 한다.

통근 조건 통과 여부와 별도로 후보 순위용 균형 점수를 계산한다.

```text
100
 - 주당 방문일 가중 평균 시간비율 패널티(최대 45)
 - 가장 불리한 목적지 시간비율 패널티(최대 25)
 - 도보 패널티(최대 10)
 - 환승 패널티(최대 10)
 - 확인하지 못한 가중치 비중 패널티(최대 25)
```

여기서 시간비율은 `실제시간 / 해당 목적지 허용시간`이다. 최종 정렬은 우선 판정 상태, 다음으로 가장 불리한 목적지, 주당 방문일 가중 평균시간을 본다. 균형 점수는 이해를 돕는 순위 보조값이지 통근 충족 하드 조건을 대신하지 않는다.

## 8. 실거래 집계 원리

### 8.1 거래 정규화

모든 국토부/API/CSV 거래는 `normalizeTransaction()`을 거친다.

- 가격 단위: 만원
- 면적 단위: 전용 ㎡
- 평당가격: `거래금액(만원) × 3.3 ÷ 전용면적(㎡)`
- 지원 거래유형: 매매, 전세, 월세
- 취소·해제 거래, 금액/면적/단지/계약월이 없는 행은 제외
- 월세는 보증금과 월세를 별도 필드로 유지하고 대표 `amountManWon`은 보증금이다

지역 비교용 면적대는 `40㎡ 미만`, `40–60㎡`, `60–85㎡`, `85–102㎡`, `102㎡ 이상` 다섯 구간이다. 반면 단지 이력은 59.7㎡, 84.9㎡처럼 **0.1㎡까지 같은 전용면적끼리** 본다.

### 8.2 평균값

월별 그룹에서 다음 값을 계산한다.

- 산술평균 거래금액
- 각 거래를 먼저 평당으로 바꾼 뒤 산술평균한 평당가격
- 중앙값, 1·3사분위수(호환·보조 통계)
- 거래 건수와 서로 다른 단지 수
- 표본 품질: 20건 이상이면서 5개 이상 단지면 높음, 5건 이상이면 보통, 그 미만은 낮음

현재 화면 대표 문구는 **평균 거래가격/평균 평당가격**을 쓴다. 중앙값 필드가 코드에 남아 있어도 사용자 대표값으로 다시 바꾸면 안 된다. 평균은 한두 건의 고가·저가 거래에 민감하므로 반드시 거래 건수와 최근 개별 거래를 함께 보여준다.

전월 변화는 월 인덱스가 정확히 1 차이인 직전월이 있을 때만 계산한다. 전년 변화도 정확히 12개월 전이 있을 때만 계산한다. 두 비교 월 중 하나라도 거래가 3건 미만이면 코어에 `lowSample` 표시가 남는다. 지역 순위는 모든 지역이 공통으로 보유한 가장 최근 월만 비교해 서로 다른 기준월을 섞지 않는다.

### 8.3 단지 이력 기간과 캐시

사용자는 1년·3년·5년(12/36/60개월)을 선택한다. 방문일 비교에 더 긴 기록이 필요하면 12→36→60개월 중 방문월을 포함하는 최소 범위로 늘리되 최대 60개월을 넘지 않는다.

단지 이력 서버는 지역코드, 단지명, `aptSeq`, 법정동, 기간, 기준월을 캐시 식별자에 포함한다. 현재월을 포함해 신고 중 자료도 화면에는 보여줄 수 있지만, 일부 월 응답이면 완전 캐시로 저장하지 않는다. 실패 시 과거의 완전 캐시가 있으면 `stale/partial`로 명확히 표시해 반환할 수 있다.

## 9. 6개월 가격 예측과 안전 게이트

### 9.1 무엇을 예측하는가

예측 대상은 기본적으로 월별 **평균 평당 실거래가격**이다. 정확한 단지 전용면적을 선택했을 때는 예측 평당가격에 `전용면적 ÷ 3.3`을 곱해 사용자가 이해하기 쉬운 예상 총 거래가격도 보여준다.

이 모델은 외부 AI 모델이나 금리·입주량·학군·정책 변수를 쓰지 않는다. 현재 구현은 오직 해당 시계열의 과거 가격과 월별 거래량 가중치로 계산하는 통계적 참고 모델이다.

### 9.2 계산 모델

1. 아직 신고가 진행 중이라고 보는 현재월·직전월, 기본 2개월을 학습에서 제외한다.
2. 월 거래수가 기준보다 작은 달을 제외한다.
3. 최근 기본 36개월 창의 평균 평당가격에 로그를 취한다.
4. 월 거래수 `min(count, 20)`을 가중치로 선형 추세를 적합한다.
5. 추세를 `phi=0.85`로 점차 약화해 1~6개월 뒤를 계산한다.

개념식은 다음과 같다.

```text
z_t = log(월 평균 평당가격)
예상(h) = exp(현재수준 + 월추세 × (1 - phi^h) / (1 - phi))
```

오차 범위는 정규분포를 가정해 임의로 붙이지 않는다. 과거 각 시점에서 그 뒤 정확히 h개월을 예측하는 시간순 rolling-origin 검증을 하고, 절대 로그오차의 유한표본 80% conformal 분위수를 위아래에 적용한다. 이것은 과거 검증에서 만든 **경험적 참고 범위**이며 미래 80% 확률을 보장한다는 뜻은 아니다.

### 9.3 공개를 허용하는 기본 조건

지역 집계 기본 게이트는 다음과 같다.

- 월별 거래 3건 이상인 유효 관측월 18개 이상
- 달력상 관측 기간 24개월 이상
- 전체 거래 50건 이상
- 마지막 유효 거래가 기준월에서 2개월보다 오래되지 않음
- 6개월 고정구간 시간순 백테스트 원점 18개 이상
- 불확실성 구간을 만들 백테스트 원점 8개 이상
- “가격이 그대로”라고 가정한 기준보다 MAE를 5% 이상 줄임
- 시간순 백테스트 평균 절대백분율오차가 20% 이하

단지 정확면적 문맥은 희소성을 고려해 월별 1건, 관측월 12개, 기간 18개월, 전체 20건, 마지막 유효 거래 4개월 이내로 일부 최소값을 완화한다. 그러나 시간순 백테스트·무변화 기준 개선·불확실성 표본·오차 상한 게이트는 그대로 적용된다.

하나라도 실패하면 숫자를 억지로 내지 않고 “예상가격 보류”와 이유를 표시한다. 단지 이력이 `partial`이면 표본 수와 무관하게 예측을 보류한다.

### 9.4 예측을 해석할 때 금지할 표현

- “AI가 6개월 뒤 가격을 맞힌다”
- “이 범위 안에 80% 확률로 들어간다”
- “금리·교통·공급·정책을 반영했다”
- “오를 것이 확정됐다/내릴 것이 확정됐다”

현재 올바른 설명은 “완결된 실거래 월의 평균 평당가격 추세가 과거 검증에서 단순 무변화보다 충분히 나았을 때만 보여주는 6개월 참고값”이다.

## 10. 방문 당시와 현재 비교

방문 기록의 `askingPrice`는 사용자가 현장에서 확인한 호가/안내가이고 실거래가가 아니다. `buildVisitBenchmark()`는 세 사실을 분리한다.

1. 방문 기록의 현장 확인가
2. 방문일 전후의 동일 거래유형·동일 전용면적 실제 거래
3. 방문일 이후에 신고된 최신 동일 조건 실제 거래

방문 당시 기준은 우선 방문일 이전 90일 거래를 사용한다. 그 안에 기본 3건이 없으면 방문일 ±90일 대칭 구간으로 넓혔다고 명시한다. 현재 기준은 방문일 이후 거래만 사용하며, 최신 거래일 기준 최근 3개월에 기본 3건 이상이면 그 평균을 쓴다. 부족하면 방문 후 최신 3건 fallback을 쓰고 낮은 신뢰도로 표시한다.

```text
방문 후 시장 변화 = 현재 실제거래 평균 - 방문 당시 실제거래 평균
현장가 괴리       = 방문 당시 현장 확인가 - 방문 당시 실제거래 평균
```

방문 후 거래가 없으면 현재 변화율을 계산하지 않는다. 현장 확인가는 시장 변화 계산에 넣지 않는다. 같은 단지라도 전용면적 허용오차 기본 0.05㎡와 거래유형이 다르면 비교하지 않는다.

## 11. 분양·청약 수집과 필터

### 11.1 수집 범위

통합 수집기는 최근 기본 730일을 대상으로 서울·경기만 남긴다.

- 청약홈: APT 분양, 잔여세대, 임의공급의 상세·주택형 API
- LH: 유형코드 `05` 분양주택, `39` 신혼희망타운 × 서울 `11`, 경기 `41`
- SH: 공식 공고 RSS 중 주택분양으로 보수적으로 분류한 항목
- LH 임대 유형코드 `06`: 현재 분양 목록에서 명시적으로 제외

청약홈은 페이지당 100건, 최대 500페이지, 요청 타임아웃 30초, 최대 3회 시도, 주택형 상세 동시성 최대 4로 수집한다. 공급원 하나가 실패해도 다른 공급원의 정상 결과를 버리지 않는다.

### 11.2 공통 스키마와 신혼 판정

각 공급원 자료를 안정 ID, 공급원, 제목, 공식 URL, 공고일, 지역/주소, 프로그램, 소유형태, 접수·발표·계약 일정, 세대수, 주택형, 전용면적, 분양가, 특별공급 수로 정규화한다.

청약홈의 프로그램 분류는 공고 제목의 마케팅 문구가 아니라 공급자가 제공한 주택구분·상세구분·임대구분·공고종류 필드를 사용한다. 신혼 대상도 다음처럼 구조화 근거가 있을 때만 확정한다.

- 공식 프로그램이 신혼희망타운
- 주택형/특별공급 행에 신혼부부 배정 세대가 1 이상

특별공급 날짜만 있고 신혼 세대 필드가 없으면 `확인 필요`로 둔다. 가격·면적·세대수가 제공되지 않으면 추정하지 않고 `null/공고문 확인`으로 유지한다.

### 11.3 공급원 장애·기준선·변경 감지

공급원마다 첫 **완전 성공** 시점을 독립 기준선으로 만든다. 첫 성공 때 이미 존재하던 공고를 모두 새 공고로 보내지 않는다.

- 공급원 전체 실패: 그 공급원의 이전 공고를 `stale`로 보존
- 공급원 부분 성공: 새로 받은 항목은 fresh, 빠진 이전 항목은 stale로 보존
- SH: RSS가 페이지네이션 없는 제한 피드이므로 최신 피드에 없다는 이유만으로 철회로 단정하지 않고 조회기간 안에서는 historical로 유지
- 세 공급원 모두 실패: 기존 정상 공개 스냅샷을 빈 파일로 덮어쓰지 않음

변경 감지는 공개에 의미 있는 필드의 정규화 결과를 fingerprint로 비교한다. 신규·업데이트·삭제·조회기간 만료를 구분하고, `stale` 또는 알림 불가 공고는 신규/업데이트 알림 대상에서 제외한다.

### 11.4 화면 필터

분양 조건은 모두 교집합으로 적용한다.

- 서울/경기 및 시·구·동 키워드
- 접수 중/예정/마감/미확인
- 공급 프로그램·공급원·분양/임대
- 공식 근거가 있는 신혼 대상만
- 최대 분양가
- 최소·최대 전용면적: 공고 주택형 중 하나라도 구간에 들어오면 통과
- 최소 공급세대
- 관심 공고, 읽지 않은 공고, 검색어

가격·면적·세대수 미공개 공고를 포함할지는 각각 독립 옵션이다. 미공개를 포함했다고 해서 조건을 충족한 값이 있다는 뜻은 아니다.

## 12. 청약 준비도와 당첨확률

청약 프로필은 브라우저에만 저장하는 자가 입력이다. 혼인 상태·기간, 무주택, 과거 특별공급, 소득·자산 확인, 자녀/신생아, 두 사람 각각의 무주택기간·부양가족·통장 가입개월·납입횟수를 받는다.

민영 일반공급 참고 점수는 현재 다음 세 항목의 기본 84점 구조만 계산한다.

- 무주택기간 최대 32점
- 부양가족 최대 35점
- 청약통장 가입기간 최대 17점

두 사람 중 입력이 완전한 점수가 높은 사람을 참고 신청자로 제안할 수 있다. 그러나 법정 기산일, 배우자 통장 합산, 세대원 판정, 지역 거주 우선, 국민주택 납입인정액 등 공고별 규칙을 자동 확정하지 않는다.

신혼부부 특별공급/신혼희망타운은 `신청 준비`, `추가 확인`, `우선 자격 확인` 상태와 확인 항목만 제시한다. 코드의 `probabilityAvailable`은 항상 `false`다. 모집 주택형별 공급 수, 실제 신청자 분포, 순위, 무효신청, 동점 추첨 정보가 없으므로 **개인 당첨확률 숫자를 만들지 않는다.** 공급비율도 개인 확률로 바꾸지 않는다.

## 13. 휴대폰·브라우저 알림

### 13.1 화면이 열려 있을 때

사용자가 브라우저 알림 권한을 허용했고 HomeHunt 코드가 실행 중이면 다음을 알릴 수 있다.

- 새 공고
- 중요 변경
- 접수 D-3/D-1

서비스 워커 기반 백그라운드 푸시는 아직 없으므로 페이지를 닫은 뒤의 전달을 보장하지 않는다. 알림 조건과 중복 키도 그 브라우저 localStorage에만 있다.

### 13.2 Telegram + GitHub Actions

배포 후 페이지가 닫혀 있어도 받는 현재 경로는 비공개 Telegram 그룹이다. 예약 workflow는 KST 07:17, 12:17, 18:17에 분양 수집과 알림을 시도한다. 수동 실행은 기본적으로 dry-run이고 사용자가 `notify`를 명시할 때만 전송한다.

알림 조건은 Repository Variables에서 읽는다.

- 서울/경기, 동네 키워드
- 신혼 대상만
- 최대 분양가
- 최소/최대 평형
- 최소 공급세대
- 가격/면적/세대수 미공개 포함 여부

다음은 보내지 않는다.

- 공급원 첫 정상 기준선의 기존 공고
- stale, 알림 불가, 마감 공고
- 중요 필드가 아닌 변경
- 이미 같은 공고 ID·fingerprint로 보낸 변경
- 공식 HTTPS 허용 도메인으로 검증되지 않은 링크

중요 변경은 접수상태·공고/마감일·접수/발표/계약 일정·공급세대·신혼/신생아 배정·대상 태그·분양가·주택형 등을 말한다. 메시지는 최대 3,500자, 한 실행 최대 5개 메시지로 묶고, 넘는 공고는 HomeHunt에서 확인하라는 요약으로 바꾼다. Telegram 429는 서버가 요청한 범위 안에서 한 번 재시도한다.

브라우저의 분양 조건과 GitHub Repository Variables는 자동 동기화되지 않는다. 같은 조건을 양쪽에 한 번씩 설정해야 한다. GitHub 예약 실행은 정확한 시각·무누락을 보장하지 않으므로 중요한 GH 공고 등 자동 수집 외 영역은 기관 공식 문자알림과 병행해야 한다.

## 14. 로컬 API 계약

로컬 서버는 `127.0.0.1`에만 바인딩하며 기본 포트는 8787이다. 주요 경로는 다음과 같다.

| 메서드/경로 | 역할 | 핵심 제한 |
|---|---|---|
| `GET /api/health` | 키 값 없이 공급자 연결·버전·카탈로그·캐시·쿼터 상태 반환 | 현재 프런트와 서버 버전 비교에 사용 |
| `POST /api/config` | 입력한 키를 현재 프로세스 메모리에 연결 | 디스크에 저장하지 않음, 서버 재시작 시 소실 |
| `GET /api/place-search?query=` | NAVER API HUB 회사/건물 검색 | 2~100자, 메모리 5분 캐시 |
| `GET /api/supply` | 공식 분양 스냅샷 또는 안전한 이전 캐시 | 3시간 캐시, 실패 후 15분 재시도 대기 |
| `GET /api/apartment-history` | 서울·경기 단지 12~60개월 매매·전월세 | 지역코드 11/41만, 동명 후보는 409 |
| `POST /api/recommendations` | 가격·기본조건 비동기 추천 시작 | 국토부 키 필요, 매매 자료 사용 |
| `GET/DELETE /api/recommendations/{id}` | 진행 조회/취소 | 작업 약 1시간 보존 |
| `POST /api/commute` | 한 출발지→한 목적지 실제 경로 | 좌표와 모드 필요 |
| `POST /api/commute/batch` | 후보 1~10×목적지 1~4 행렬 | 호출 사전검사, 대중교통 원호출 상한 0~40 |
| `GET /api/commute/quota` | Kakao/TMAP 로컬 장부 상태 | 실제 공급자 콘솔과 다를 수 있음 |

요청 본문은 최대 16KiB다. 브라우저 Origin이 있으면 localhost/127.0.0.1만 CORS 허용한다. 이것은 인터넷 공개를 막는 로컬 경계이지 사용자 인증은 아니다.

## 15. 비밀키와 개인정보 보안

### 15.1 키 저장 원칙

- 실제 키는 Git 제외 `homehunt/.env`, 프로세스 환경변수, GitHub Actions Secrets 또는 Firebase Secret Manager에만 둔다.
- `.env.example`에는 변수 이름만 둔다.
- `.env`는 로컬 평문 파일이므로 화면 캡처·채팅·커밋을 금지한다.
- 로컬 실행기는 허용 목록의 환경변수만 읽고 이미 존재하는 프로세스 환경변수를 우선한다.
- 화면의 `키 연결`은 `/api/config`를 통해 서버 메모리에만 넣으며 파일에 쓰지 않는다.
- `/api/health`와 설정 응답은 키 값이 아니라 `configured: true/false`만 돌려준다.
- NAVER Maps Web SDK Client ID는 지도 로딩용 공개 클라이언트 설정이고, Directions/지역 검색 Client Secret은 서버 밖으로 내보내지 않는다.
- Telegram 토큰과 채팅 ID는 Actions Secrets에만 둔다. Repository Variables에는 넓은 지역·예산 조건만 두고 회사/집 주소나 청약 프로필을 넣지 않는다.

### 15.2 개인 기록 원칙

방문 주소, 메모, 회사 좌표, 청약 자가입력은 현재 브라우저 저장소에 남는다. 공개 Firestore나 공개 JSON으로 자동 전송하지 않는다. 두 사람 간 자동 공유가 필요하면 Firebase Authentication과 사용자별 보안규칙부터 만든 뒤 이전해야 한다. PIN 화면만으로는 데이터 접근 통제가 되지 않는다.

### 15.3 크롤링 원칙

네이버 부동산 현재 매물 페이지를 크롤링하지 않는다. 공식 매물 API 없이 화면 HTML을 자동 수집하면 약관·차단·구조 변경에 취약하기 때문이다. 현재 매물은 외부 링크에서 사람이 확인하고, HomeHunt 계산에는 국토부 신고 실거래만 사용한다.

## 16. 실패 시 보이는 상태가 의미하는 것

| 상태 | 의미 | 데이터 취급 |
|---|---|---|
| 단지 검색 성공·가격 서버 미연결 | 카탈로그 후보만 찾음 | 가격을 생성하지 않음 |
| 국토부 키 필요 | localhost는 켜졌으나 실거래 인증 불가 | 키 연결 후 재시도 |
| 일부 월 실패 | 단지 이력 또는 추천 범위가 불완전 | 완전 캐시 미덮어쓰기, 추천은 실패 시군구 전체 제외 |
| stale cache | 상류 장애로 이전 완전 자료 사용 | 오래된 자료임을 표시, 예측 보류 가능 |
| 통근 pending | 키 없음, 경로 없음, 일부 목적지 미확인 또는 조건 fingerprint 변경 | 시간 충족으로 세지 않음 |
| Kakao screening | 광역 1차 확인만 완료 | 혼합 모드에서는 TMAP 최종 결과로 보지 않음 |
| 분양 stale/historical | 공급원 실패 또는 SH 제한 피드에서 사라짐 | 삭제로 단정하지 않고 알림 억제 |
| 예측 보류 | 표본·최신성·백테스트·기준모델 개선·부분응답 게이트 실패 | 숫자를 표시하지 않음 |

## 18. 다음 고도화가 반드시 해결해야 할 현재 한계

아래는 “설계 가능성”이 아니라 현재 코드와 화면 사이에서 확인된 실제 미완성 범위다.

1. **역 도보 조건 미판정**: 입력/저장은 되지만 역 위치·도보 경로 데이터로 후보를 걸러내지 않는다.
2. **목적지별 조건 UI 부족**: 주당 방문일만 개별이고 교통수단·허용시간·출발시각은 A–D에 공통 적용된다.
3. **60분 문구 경계**: 화면의 `미만`과 코어의 `<=`가 다르다.
4. **Kakao 시간 기준 한계**: 현재 요청은 출발시각을 보내지 않으므로 TMAP 최종 검증과 동급으로 표현할 수 없다.
5. **실거래 추천 기간이 짧음**: 조건 추천은 최근 1~6개월 거래만 보며 거래가 없는 단지는 예산 가능성을 판정하지 못한다.
6. **추천은 매매 전용**: 단지 실거래 화면은 전세를 보지만 전체 맞춤 추천의 가격 하드 필터는 매매만 사용한다.
7. **현재 매물 없음**: 매물 수, 호가, 관리비, 동·향·층별 현재 판매 상태는 제공하지 않는다.
8. **단지 생활정보 부족**: 역 접근성, 주차대수, 학군, 관리비, 커뮤니티, 재건축 상태 등은 아직 공식 데이터와 연결되지 않았다.
9. **예측 외생변수 없음**: 금리, 입주 예정 물량, 전세가율, 지역 지수, 정책 변화가 모델에 들어가지 않는다.
10. **공개 데이터 기준선 미완성**: 현재 커밋된 지역 집계와 분양 파일은 비어 있거나 API 승인 대기 상태다.
11. **배포 백엔드 미완성**: 전체 추천·장소·통근은 localhost에서만 동작한다.
12. **개인정보 공유 없음**: 두 사람 브라우저 간 방문기록·목적지·분양 관심 자동 동기화가 없다.
13. **백업 범위 제한**: 방문/비교만 JSON 백업되며 관심 후보·목적지·분양조건·청약 프로필은 빠진다.
14. **당첨확률 미제공**: 데이터 부족 때문에 의도적으로 숫자 확률을 만들지 않는다.
15. **GitHub/Telegram 예약 보장 없음**: 예약 시각 지연·비활성화 가능성이 있어 기관 공식 알림을 대체하지 못한다.

## 19. 고도화 시 지켜야 할 회귀 방지 규칙

1. 검색 실패 때 예시 가격이나 이전 검색 결과를 새 결과처럼 남기지 않는다.
2. `실거래 평균`, `현장 확인가`, `현재 매물 호가`, `분양가`를 한 숫자로 합치지 않는다.
3. 공급면적과 전용면적을 표시만 함께 할 수는 있어도 필터 계산에서 몰래 바꾸지 않는다.
4. 부분 월 자료로 추천하거나 예측하지 않는다.
5. Kakao 선별 결과를 TMAP 출근시각 최종 검증으로 승격하지 않는다.
6. 통근 경로가 없는 후보를 직선거리만으로 `1시간 충족` 처리하지 않는다.
7. 목적지가 바뀌면 저장 후보의 이전 통근 결과를 재검증한다.
8. 신혼 키워드만으로 공식 신혼 배정이 있다고 확정하지 않는다.
9. 공급 비율이나 자가 점수를 개인 당첨확률로 바꾸지 않는다.
10. 개인 주소·메모·청약 프로필·FCM 토큰을 공개 Git/Firestore에 저장하지 않는다.
11. 실제 키를 코드·문서·테스트 fixture·URL·로그·스크린샷에 남기지 않는다.
12. 네이버 부동산 HTML 크롤링을 현재 실거래 데이터의 대체재로 추가하지 않는다.
