# HomeHunt 다중 통근·아파트 의사결정 설계 보고서

- 조사 기준일: 2026-09-04 (Asia/Seoul)
- 대상: 서울·경기 아파트, 최대 4개 회사·주요 목적지
- 구현 기준: HomeHunt 2.0 설계 및 로컬 실거래 서버
- 근거 구분: **확인된 사실**은 공식 문서·공공 데이터·원 논문, **설계 결정**은 그 근거를 HomeHunt 목적에 적용한 판단이다.
- 신뢰도 표기: `높음`은 공식 명세·원자료로 직접 확인, `보통`은 공식 자료에 기반하지만 실제 운영 조건의 영향을 받음, `제한적`은 표본·가정 의존도가 큼을 뜻한다.

## Executive Summary

HomeHunt의 핵심은 “한 회사 주변의 싼 아파트 찾기”가 아니라, **3~4개의 실제 목적지를 모두 감당할 수 있는 후보 중 예산·면적·세대수·연식이 맞는 아파트를 찾고, 그 시장과 방문 이후의 변화를 판단하는 것**이다. 따라서 검색·통근·가격·예측을 하나의 숫자로 섞지 않고 다음 네 단계의 증거로 나눈다.

1. 국토교통부 실거래로 예산·면적 조건에 맞는 후보를 만든다.
2. 모든 목적지까지의 직선거리는 후보 정렬용으로만 쓰고, 합격 판정에는 쓰지 않는다.
3. 대중교통 경로가 확인된 후보만 통근 제한을 충족했다고 표시한다. 여러 회사 중 **가장 불리한 통근시간을 먼저 최소화**하고, 주당 출근일을 반영한 가중 평균과 도보·환승 부담을 보조 점수로 사용한다.
4. 정확한 단지·전용면적 실거래에서 가격 흐름과 방문 당시 대비 현재 변화를 계산한다. 데이터가 부족하거나 단순 “가격 유지” 기준보다 예측력이 낫지 않으면 숫자 예측을 보류한다.

TMAP의 대중교통 무료 상품은 조사일 기준 일 10건이다. 여러 Application을 만들어 무료량을 우회하는 방식은 약관상 허용되지 않으며 제품 설계로도 부적절하다. 권장 운영은 두 가지다.

- **무료 하이브리드:** Kakao 대중교통 REST로 넓게 검증한 뒤, 사용자가 고른 상위 2개 후보 × 회사 4곳 = TMAP 8건만 동일한 출근시각으로 정밀 확인하고 2건을 예비로 남긴다.
- **정확도 우선:** TMAP 대중교통 요약 종량제를 사용한다. 공식 단가가 건당 0.55원이라면 후보 50곳 × 회사 4곳 = 200건은 약 110원/검색, 월 30회는 약 3,300원이다. 부가세·최소 과금·계약 조건은 신청 시 다시 확인해야 한다.

Kakao는 조사일 기준 첫 Kakao Maps 앱에 대중교통 길찾기 일 1,000건을 제공하며 초과 또는 두 번째 앱부터 건당 10원 정책을 안내한다. 다만 출발시각 파라미터가 없으므로 넓은 후보 선별에 적합하고, 평일 08:00처럼 같은 시각 비교가 필요한 최종 판정은 `searchDttm`을 지원하는 TMAP이 더 적합하다.

화면은 한 페이지 첫 화면에서 `조건 → 목적지 A~D → 후보 지도 → 통근·가격 결론`이 보이도록 구성한다. 지도에는 목적지 A~D, 예산 후보, 방문 단지를 함께 표시하고, 클러스터는 `전부 충족 / 혼합 / 미확인`을 구분한다. 아래 상세 영역에만 거래 이력, 예측 진단, 방문 당시 대비 현재를 둔다. D3는 복잡한 다목적지 행렬이 실제로 필요할 때만 도입하고, 지도는 NAVER 지도 오버레이, 짧은 시계열은 기존 Chart.js를 유지하는 편이 의존성과 유지보수 비용이 낮다.

## Detailed Analysis

### 1. 의사결정 모델: “가까운 곳”보다 “모두 감당 가능한 곳”

#### 1.1 필수 조건과 순위 조건을 분리한다

후보 아파트 `i`, 목적지 `d`에 대해 필수 통근 조건은 다음과 같다.

```text
모든 필수 목적지 d에 대해
  실제 경로가 확인됨
  AND travelTime(i, d) ≤ maxMinutes(d)
```

한 목적지라도 경로가 없으면 `미확인`, 제한을 넘으면 `초과`다. 직선거리나 다른 목적지의 좋은 결과로 이를 상쇄해 `충족`으로 만들지 않는다.

필수 조건을 통과한 후보의 순위는 다음 순서가 적합하다.

1. `max(travelTime / 허용시간)`가 작은 후보: 가장 힘든 회사 통근을 우선 개선하는 minimax 원칙
2. 주당 출근일을 가중치로 한 평균 통근시간
3. 총 도보시간·환승 횟수 부담
4. 가격 여유, 면적, 세대수, 연식 같은 주거 조건

예를 들어 회사 A는 주 4일, B는 주 1일이라면 평균 점수에는 A의 비중을 크게 주되, B가 허용시간을 넘으면 여전히 탈락시킨다. 사용자가 “모든 회사 60분 이내”가 아니라 “주 1회 가는 곳은 80분 허용”을 원하면 목적지별 제한시간을 따로 설정하는 것이 점수 가중치보다 투명하다.

#### 1.2 3단계 통근 검증

```text
[0] 가격·면적·세대수·연식 실거래 필터
      ↓
[1] 회사 A~D와 후보 간 직선거리 프록시
    - 합격 판정 금지
    - 지나치게 먼 후보 제거·경로 호출 순서 결정
      ↓
[2] Kakao 대중교통으로 넓은 후보 검증
    - 일 1,000건 범위의 1차 실제 경로
    - 출발시각 고정 비교에는 한계
      ↓
[3] 사용자가 고른 상위 후보만 TMAP 정밀 검증
    - 평일 08:00 등 같은 searchDttm
    - 총시간·환승·도보시간 비교
```

자동 검색 한 번으로 TMAP 10건을 모두 소진하면 사용자가 정말 비교하고 싶은 후보를 확인할 수 없다. 따라서 검색 버튼은 가격 후보와 프록시를 만들고, 별도 `상위 후보 정밀 검증` 버튼이 예상 호출 건수·오늘 남은 건수를 보여준 뒤 호출하게 한다. 개별 후보 카드에도 `이 후보만 검증`을 둔다.

#### 1.3 공급자별 역할과 비용

| 공급자 | 적합한 역할 | 조사일 기준 정책 | 설계 판단 |
|---|---|---|---|
| TMAP 대중교통 요약 | 같은 미래 출근시각의 최종 비교 | FREE 일 10건, 종량 요약 0.55원/건 | 무료는 상위 2곳×4목적지에 사용하거나 종량제로 전환 |
| TMAP 대중교통 전체 | 상세 구간 표시가 꼭 필요할 때 | 종량 0.88원/건 | 기본 검색에는 과함. 요약 결과로 충분하면 제거 |
| Kakao 대중교통 REST | 넓은 후보의 실제 대중교통 1차 선별 | 첫 Maps 앱 일 1,000건, 초과·두 번째 앱 10원/건 | 무료 하이브리드의 1차 공급자 |
| NAVER Directions 5 | 자동차 통근시간 | 자동차 경로 API | 자동차를 선택한 목적지만 병행 |
| ODsay Basic | 대중교통 경로 | 2026-08-20부터 일 30건 | 기본 공급자로는 규모가 부족 |
| Google Routes | 글로벌 경로·행렬 | Google 지도 서비스 약관 적용 | NAVER 지도와 혼용 제약, 국내 대중교통 커버리지 한계로 제외 |

TMAP 대중교통 요약은 `searchDttm`, 총 소요시간, 환승 횟수, 총 도보시간을 제공하므로 최종 비교에 필요한 정보가 이미 있다. 전체 상세 경로를 모든 후보에 호출하는 기능은 비용과 화면 복잡도를 늘리므로 기본 흐름에서 뺀다.

TMAP 약관상 결과 저장 후 24시간을 넘겨 재사용해서는 안 된다. HomeHunt는 경로 원문을 영구 DB나 Git에 넣지 않고 메모리 캐시를 24시간보다 짧게 유지해야 한다. 날짜별 사용량 장부에는 호출 수와 공급자만 저장하고 경로 결과를 장기 보관하지 않는다. 무료 쿼터를 여러 프로젝트로 회피하는 방식도 사용하지 않는다.

#### 1.4 역 접근성은 별도의 증거다

“역에서 도보 10~20분”과 “회사까지 대중교통 60분”은 같은 조건이 아니다. 역이 가까워도 환승이 많거나 반대 방향일 수 있고, 역이 조금 멀어도 광역버스 직행이 더 빠를 수 있다.

- K-apt의 지하철역·버스정류장 거리: 생활권 및 역 접근 선호
- 대중교통 경로의 도보 구간·환승·총시간: 실제 회사 통근 판정

K-apt 역거리 연결 전에는 숫자 입력칸 자체가 실제로 작동하는 필터처럼 보이므로 화면에서 제거한다. 대신 연결된 대중교통 경로의 총 도보시간과 환승 횟수를 바로 보여준다. K-apt를 연결한 뒤에도 역 접근성은 회사 통근 하드 조건과 섞지 않고 생활권 선호로 별도 제공한다.

### 2. 아파트 가격 구성과 추세

#### 2.1 실거래 조회 범위

국토교통부 아파트 매매·전월세 OpenAPI는 법정동 코드 앞 5자리와 계약년월 6자리로 월별 데이터를 조회한다. 이는 “1년만 제공”한다는 뜻이 아니다. 여러 계약년월을 반복 요청하면 3년·5년 이력을 만들 수 있다. 실거래가 공개시스템의 웹 다운로드 `최대 1년` 문구는 한 번의 다운로드 범위 제한이며 OpenAPI 전체 역사 제한과 구분해야 한다.

HomeHunt는 다음 원칙을 유지한다.

- 매매와 전세를 분리한다.
- 단지명뿐 아니라 실제 전용면적을 0.1㎡ 단위로 나눠 다른 크기의 거래를 섞지 않는다.
- 1·3·5년을 선택할 수 있게 하되, 최근 현재월과 직전월은 예측 학습에서 제외한다.
- 거래가 없는 달은 0원이 아니라 결측으로 둔다.
- 선택 범위, 실제 거래가 있었던 개월 수, 총 거래 수, 마지막 계약일을 함께 보여준다.
- 일부 월 수집 실패 응답이 완전 캐시를 덮어쓰지 않게 한다.

가격 내부 단위는 국토부와 같은 만원으로 유지하고 화면은 공통 formatter를 쓴다.

- `11,000만원` → `1억 1,000만원`
- `60,000만원` → `6억원`
- `62,500만원` → `6억 2,500만원`

면적은 공급면적 자료가 없으면 `34평형`으로 추정하지 않고 `전용 84.9㎡ · 약 25.7평`처럼 표시한다. 계산은 `전용면적㎡ ÷ 3.305785`다.

#### 2.2 후보 지역의 “구성”을 먼저 보여준다

최적 입지를 하나의 1등 단지로만 보여주면 시장 선택지가 보이지 않는다. 지도와 요약 패널에서 필터 통과 후보를 다음 축으로 집계해야 한다.

- 지역: 시·구·동별 후보 수와 예산 충족 비율
- 가격: 1억원 단위 또는 데이터 기반 구간별 후보 수
- 면적: 전용 59㎡·74㎡·84㎡ 등 실제 거래 면적대
- 연식: 5년 이하, 6~10년, 11~20년, 20년 초과
- 규모: 500세대 이상 여부와 세대수 구간
- 통근: 모든 목적지 충족, 일부 초과, 경로 미확인

사용자가 지도에서 구역이나 클러스터를 누르면 위 구성이 같은 필터 범위로 다시 계산되어야 한다. 그래야 “6억 이하가 존재하는 지역”과 “한 건만 우연히 거래된 지역”을 구분할 수 있다.

#### 2.3 상승·하락의 해석

화면의 월별 가격은 같은 단지·거래유형·정확 전용면적 거래금액의 산술평균이다. 평균 평당가격은 각 거래를 `거래금액 × 3.3 ÷ 전용면적`으로 바꾼 뒤 평균하며, 1평은 약 3.3㎡다. 이는 동일한 주택 한 채의 가격 변화가 아니므로 층·동·거래 구성과 극단 거래 때문에 시장이 그대로여도 움직일 수 있다. 따라서 화면에는 다음을 함께 표시한다.

- 정확 면적 월 평균가격·평균 평당가격과 거래량
- 최근 3개월 또는 충분한 최근 거래 기준값
- 지역·면적대 가격지수 또는 지역 추세
- 표본 수, 마지막 거래일, 최근월 신고 진행 경고

한국부동산원은 평균가격 같은 수준값을 표본 구성 변화에 민감한 값으로 설명하며 지역 변동률 시계열은 가격지수를 활용하도록 안내한다. 국제 RPPI 지침도 품질 구성 문제를 다루기 위해 층화·헤도닉·반복매매 기법을 제시한다. HomeHunt의 월 평균가는 이해하기 쉬운 탐색 지표이며 공식 감정가나 완전한 가격지수가 아니다.

### 3. 예측: 숫자를 만드는 기능보다 틀린 숫자를 숨기는 기능

#### 3.1 데이터 안전 게이트

최근 신고가 진행 중인 현재월과 직전월을 학습에 넣으면 인위적인 거래량 감소와 구성 왜곡이 생길 수 있다. 기본 모델은 두 달을 제외하고 다음 조건을 확인한다.

- 충분한 유효 월과 총 거래 수
- 마지막 거래의 최신성
- 결측이 지나치게 많지 않은지
- 일부 월 API 실패가 없는지
- 예측 목표 시점에 맞춘 시간순 rolling-origin 검증 표본 수

6개월 예측은 최소 18개 rolling origin, 12개월 예측은 최소 12개 origin을 기본 진단 기준으로 둔다. 데이터가 부족하면 `예측 보류`가 정상 결과다.

#### 3.2 단순 기준보다 나은 경우만 공개한다

모델은 과거 각 시점에서 당시까지의 자료만 학습하고 실제 미래값을 맞혀 보는 rolling-origin 방식으로 평가한다. 비교 기준은 복잡한 모델이 아니라 “현재 가격이 그대로 유지된다”는 no-change 예측이다.

- MAE: 평균 절대 오차
- MASE: no-change 기준으로 정규화한 오차
- Skill: no-change 대비 개선율
- 방향 적중은 보조 정보이며 단독 공개 기준이 아니다.

HomeHunt는 예측 모델의 오차가 no-change보다 **5% 이상 개선**되고 최소 검증 표본을 충족할 때만 숫자 예측을 공개한다. 그렇지 않으면 실거래 추세선과 데이터 상태만 보여준다. 이는 “늘 숫자가 나오는 예측”보다 의사결정에 안전하다.

#### 3.3 예측 범위

범위는 과거 시간순 예측 오차의 경험적 분포를 이용한 conformal 방식으로 만든다. `80% 신뢰구간`처럼 모수 가정을 암시하지 않고 `과거 오차 기반 참고범위`로 부른다. 시계열은 독립·동일분포가 아니므로 구조적 시장 변화가 있으면 포함률이 무너질 수 있으며, 실제 순차 포함률을 계속 기록해야 한다.

거래가 적은 단지는 장기적으로 같은 동·구·전용면적대 추세를 부분 풀링하는 소지역 추정이 유용할 수 있다. 다만 개별 단지 값과 지역 보정값의 기여도를 화면에서 분리해 보여야 한다.

### 4. 방문 당시 대비 현재

방문 기록의 확인가는 실거래가 아니라 매도 호가, 중개사 안내가 또는 협상 전 금액일 수 있다. 이를 최신 실거래 평균과 직접 빼서 “방문 후 8% 상승”이라고 표시하면 두 종류의 가격을 섞는 오류가 생긴다.

올바른 비교는 세 값을 분리한다.

1. **방문 당시 실제 시장 기준:** 방문일 이전 90일의 같은 단지·거래유형·가장 가까운 정확 면적 실거래. 표본이 없을 때만 방문일 전후 ±90일로 넓히고 이를 표시한다.
2. **현재 실제 시장 기준:** 방문일 이후의 같은 조건 실거래만 후보로 삼은 뒤, 최신 거래일을 기준으로 최근 3개 달력월을 사용한다. 이 기간의 표본이 부족해 최신 거래 N건으로 보완할 때도 **방문일 이전·당일 거래는 절대 섞지 않는다**. 특히 방문 후 거래가 1~2건뿐이면 값과 함께 `희소 표본 · 신뢰도 낮음`을 표시한다.
3. **방문 호가 차이:** 방문 때 확인한 가격과 방문 당시 실제 시장 기준의 차이. 시장 상승률과 별도 카드로 표시한다.

따라서 화면의 핵심 문구는 `방문 당시 실거래 기준 → 현재 실거래 기준: +X%`이고, `방문 호가는 당시 실거래보다 Y% 높음/낮음`은 보조 설명이다. 방문 후 실거래가 1~2건뿐인 변화율은 낮은 신뢰도임을 함께 표시하며, 방문 후 거래가 전혀 없거나 면적 연결이 불확실하면 변화율을 만들지 않고 `보류 · 방문 후 거래 없음`으로 표시한다.

### 5. 한 화면 중심 UI 설계

#### 5.1 첫 화면에 남길 것

데스크톱 첫 화면의 정보 위계는 다음과 같다.

```text
[가격·면적·세대수·연식] [목적지 A~D] [예산 후보 찾기]
[예산 후보 수] [통근 확인 수] [최적 균형] [최악 통근] [오늘 남은 정밀 호출]
[지도: 목적지 A~D + 후보/클러스터] [순위 목록: 가격·최악/평균 통근·면적]
```

- 자연어 조건 읽기는 보조 도구로 접고 직접 필터가 기본이다.
- 목적지는 정확한 주소를 외우는 입력칸이 아니라 회사·건물 검색 결과 또는 지도 클릭으로 추가한다.
- A~D 핀 색은 목록의 목적지 행과 동일하게 유지한다.
- 후보 클러스터가 서로 다른 상태를 포함하면 첫 후보 색으로 칠하지 않고 `혼합`으로 표현한다.
- 결과 기본 범위는 가격 후보 전체이며 `모두 충족`, `미확인`을 명시적으로 전환한다. 미확인 후보를 충족 후보처럼 보이게 하지 않는다.
- 상위 정밀 검증 버튼에는 `예상 8건 · 오늘 10건 중 2건 남음`처럼 비용·쿼터를 실행 전에 보여준다.

#### 5.2 아래로 내려도 되는 것

- 정확 면적 1·3·5년 거래 차트
- 예측 백테스트 MAE·MASE·skill과 참고범위
- 지역·가격·면적·연식 구성 차트
- 방문 당시 대비 현재 상세
- API 연결·키 상태·CSV 재수집 같은 운영 도구

연결 상태와 CSV 재수집은 중요한 운영 기능이지만 집을 고르는 핵심 작업은 아니다. 상단 주 내비게이션의 동일한 비중을 줄이고 `설정` 또는 접힌 진단 영역으로 옮기는 것이 적합하다.

#### 5.3 시각화 라이브러리 결정

NAVER 지도에는 공급자와 맞는 네이티브 Marker·Overlay·클러스터를 사용한다. 짧은 월별 거래선과 거래량은 기존 Chart.js로 충분하다. D3를 추가하면 다중 목적지 시간 행렬, 지역별 가격 분포처럼 표준 차트로 표현하기 어려운 상호작용에는 도움이 되지만, 단순 선 그래프를 다시 만드는 용도로는 번들·접근성·유지보수 비용만 늘어난다. 현 단계에서는 새 라이브러리 도입보다 정보 구조와 상태 색의 정확성이 우선이다.

### 6. 데이터 저장과 배포

GitHub Pages는 정적 파일을 읽을 수 있지만 브라우저가 저장소의 JSON 파일을 직접 수정할 수는 없다. 로컬 파일 DB를 GitHub에 올리면 배포 시점의 스냅샷은 볼 수 있어도 새 검색·방문 기록이 자동으로 여러 기기에 공유되지는 않는다.

권장 분리는 다음과 같다.

- 현재 로컬 개발: `.env`의 비밀키 + localhost 프록시, 브라우저 IndexedDB/localStorage 방문 기록
- 공개 정적 데이터: 아파트 카탈로그·공개 집계 JSON
- Firebase 전환 후: 인증된 사용자 방문 기록·관심 후보·검색 메타데이터
- Firebase Functions/Secret Manager: 국토부·NAVER·Kakao·TMAP 서버 키와 외부 API 호출
- 경로 원문: TMAP 약관을 지키는 24시간 미만 단기 캐시만 사용

`.env`, 서버 Client Secret, TMAP appKey는 Git·브라우저 저장소·공개 응답에 포함하지 않는다. 이미 화면이나 이미지에 노출된 Secret은 재발급하는 것이 안전하다.

## Recommendations

### 즉시 적용할 설계

1. **다중 목적지 모델을 기본으로 한다.** 회사·주요 목적지 1~4개, 목적지별 주당 방문일·허용시간·교통수단을 저장하고 A~D로 표시한다.
2. **자동 TMAP 대량 호출을 제거한다.** 검색은 예산 후보와 거리 프록시까지만 수행하고, 상위 후보 또는 개별 후보의 정밀 검증을 사용자가 명시적으로 실행한다.
3. **무료 하이브리드를 기본값으로 한다.** Kakao 대중교통으로 후보를 넓게 확인하고 TMAP 무료 10건은 상위 2개×4목적지에 배분한다. 정확도와 반복 검색이 더 중요하면 TMAP 요약 종량제로 전환한다.
4. **역 거리 미연결 하드 필터를 제거한다.** K-apt 또는 검증된 보행 경로가 연결되기 전에는 `선호·미확인`으로만 보인다.
5. **모든 목적지 충족을 명시한다.** 최악 통근, 가중 평균, 목적지별 시간·환승·도보를 같은 카드에 표시한다.
6. **방문 호가와 실거래 변화를 분리한다.** 방문일 실거래 기준→현재 실거래 기준의 변화와 방문 호가 괴리를 각각 보여준다.
7. **예측 안전 게이트를 기본값으로 한다.** 불완전월 제외, horizon별 rolling-origin, no-change 기준, 5% skill, 최소 표본, 경험적 참고범위를 모두 통과해야 숫자를 공개한다.
8. **운영 UI를 아래로 내린다.** CSV 재수집·연결 진단·키 설정은 `설정`으로 이동하고 첫 화면에는 조건·지도·결론만 남긴다.

### 다음 데이터 보강 순서

1. K-apt 기본·상세 정보로 세대수, 주차, 승강기, 역·버스정류장 거리, 편의시설을 보강하되 미매칭 단지를 탈락시키지 않는다.
2. 한국부동산원 지역 아파트 매매가격지수를 결합해 개별 단지의 희소 거래를 지역 추세와 분리한다.
3. 목적지별 평일 출근시간을 2~3개 시각으로 반복 표본화해 “한 번의 경로 결과”가 아닌 안정적인 통근 범위를 제공한다.
4. 후보 지역 구성을 시·구·동, 가격, 면적, 연식, 세대수로 집계하고 지도 선택과 양방향 필터링한다.
5. Firebase Authentication과 Functions로 이전해 두 사람의 방문 기록은 공유하되 API Secret과 TMAP 경로 원문은 보호한다.

## Caveats

- **API 정책은 변한다.** TMAP·Kakao·ODsay의 일일량과 단가는 2026-09-04 공식 문서 기준이며 실제 신청 화면·계약서가 우선한다.
- **무료량 우회는 해결책이 아니다.** TMAP Application을 여러 개 만들어 일 10건을 반복 확보하는 방식은 약관·운영 안정성 모두에 문제가 있으므로 구현하지 않는다.
- **대중교통 시간은 확정값이 아니다.** 시간표 개편, 실시간 지연, 환승 보행, 출발시각에 따라 바뀐다. Kakao의 현재 경로와 TMAP의 특정 `searchDttm` 결과를 같은 의미로 섞지 않는다.
- **자동차와 대중교통은 분리한다.** NAVER Directions 5 자동차 결과를 대중교통 대체값으로 사용하지 않는다.
- **최신 실거래는 불완전하다.** 신고 지연·해제·정정이 있어 현재월과 직전월은 예측 학습에서 제외하고 화면에도 진행 중임을 표시한다.
- **평균가격은 가격지수가 아니다.** 극단 거래와 거래 구성 변화에 민감하며 동·향·수리 상태·내부 상태를 통제하지 못한다.
- **예측은 감정평가가 아니다.** 안전 게이트를 통과해도 과거 오차 기반 참고치이며 금리·정책·입주물량 같은 구조 변화를 보장하지 않는다.
- **K-apt 포괄성은 제한된다.** 의무관리·관리비 공개 대상 제도 범위 때문에 소규모 단지의 상세 필드가 비어 있을 수 있다. 누락은 탈락이 아니라 `공식 상세 미확인`이다.
- **GitHub Pages는 쓰기 가능한 DB가 아니다.** Git에 포함된 JSON은 배포 스냅샷이고, 여러 기기의 최신 방문 기록 공유에는 인증된 데이터베이스가 필요하다.
- **비밀키를 정적 페이지에 넣으면 안 된다.** `.env`는 로컬 서버만 읽고, Firebase 배포 시 Secret Manager와 서버 함수로 이전한다.
