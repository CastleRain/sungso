# 둘의 생활 앱 확장 계획

작성·공식 문서 확인: **2026-09-14**. 상태: **세 생활 앱 기본틀 공개 배포 완료 · 현재 운영 일정 대조 완료**. 생활 기록은 UID별 브라우저 저장이며 공동 저장과 이미지 기능은 후속 계획이다.

사용자가 요청한 대문 개편과 장보기부터 시작하는 전체 생활 앱의 기본틀을 로컬에 구현했다. 기존 앱 6개를 보존하고 `우리 식탁`, `우리 발자국`, `우리 결혼`을 추가했다. 신규 생활 기록은 공통 Google 회원 확인 뒤 **UID별 브라우저 `localStorage`에만 저장**한다. 다른 기기나 상대 계정과의 자동 공동 저장, 사진 원본 업로드, NAVER 즐겨찾기 자동 동기화는 아직 구현하지 않았다.

이번 범위에서 신규 Firestore 컬렉션·인증 범위·보안 규칙·외부 계정·요금제와 운영 데이터를 변경하지 않았다. 사용자가 지정한 현재 공개 Dates의 일정으로 로컬·공개 홈을 대조했으며, `dbdee6c`를 `master`에 반영했다. [Pages 34839107014](https://github.com/CastleRain/sungso/actions/runs/34839107014)의 검사·서비스 번들·배포 성공과 공개 자산 25/25개 일치를 확인했다.

## 현재 구성: 큰 공간 세 개, 필요한 기능은 그 안의 탭으로

| 공간 | 구현한 기본 기능 | 같은 공간에 두는 이유 | 별도 공간과 연결 |
|---|---|---|---|
| **[우리 식탁](../../../../apps/table/README.md)** | 장보기, 저장된 레시피·식당에서 먹을 후보 고르기, 둘만의 레시피 | 오늘 먹을 것을 정하고, 필요한 재료를 사고, 해 먹은 방법을 남기는 흐름이 이어진다. | 외식 후보는 `우리 발자국`의 같은 장소 기록을 보여준다. |
| **[우리 발자국](../../../../apps/footprints/README.md)** | 식당·카페·데이트 장소, 가고 싶은 곳, 방문 기록, 외부 HTTPS 앨범 링크 | 한 번의 외출에 장소·날짜·메모·앨범이 함께 쌓인다. 장소·방문·사진첩 탭으로 나눈다. | `우리 식탁`의 외식 후보와 같은 계정·브라우저의 장소 ID를 사용한다. |
| **[우리 결혼](../../../../apps/wedding/README.md)** | 하객노트, 초대·참석 상태와 인원, 준비할 일, 기존 관련 앱 입구 | 결혼이라는 한 프로젝트 안에서 확인할 정보를 묶는다. | 청첩장·WeCost·Honeymoon·Travel·Dates의 기존 화면으로 이동한다. |

한 앱으로 묶는 기준은 **같은 기록을 사용하고 한 행동이 다음 행동으로 이어지는가**다. 메뉴 이름이 다르다는 이유만으로 앱을 하나씩 늘리지 않는다. 예산·여행처럼 이미 독립된 저장 계약과 풍부한 화면이 있는 기능은 기존 앱을 유지한다. 결혼 공간은 기존 공개 주소와 직접 링크를 보존하며, 연결 화면과 신규 하객·준비 기록만 소유한다.

대문의 홈 바로가기는 기존 6개 앱 중 최대 4개를 고르는 계약을 유지한다. 모든 앱 화면에는 기존 6개와 신규 생활 앱 3개를 합쳐 **9개**를 보여주며, 휴대폰에서는 **6개 + 3개**로 페이지를 나눈다. 신규 앱 ID는 기존 공유 홈 설정에 넣지 않는다. 향후 생활 앱 바로가기·공동 저장을 추가할 때 저장 계약을 별도로 검토한다.

## 로컬 기본틀과 남은 확장

장보기부터 시작해 세 공간의 기본 기록 동작을 구성했다. 각 앱은 빈 목록에서 시작하며 샘플을 자동 저장하지 않는다. 현재 같은 계정·브라우저의 기록을 연결하는 단계이고, 두 사람이 서로 다른 기기에서 같은 기록을 함께 편집하는 단계는 남아 있다.

| 기능 | 구현한 로컬 기본틀 | 남은 확장 |
|---|---|---|
| 장보기 | 품목·수량·단위·분류·메모, 구매 체크·되돌리기, 수정·삭제 | 두 계정 공동 목록, 자주 사는 품목 전용 모음. 영수증 인식·최저가 수집·자동 주문은 별도 검토다. |
| 장소·방문 기록 | 장소명·지역·종류·주소·지도 링크·가고 싶음, 같은 장소의 여러 방문 날짜·메모 | 공동 방문 기록, 지도 위 표시, 지역 탐색 보강. NAVER 즐겨찾기 자동 동기화는 미구현이다. |
| 둘만의 레시피·뭐 먹지 | 재료·순서·팁, 저장한 레시피와 식당·카페에서 후보 고르기, 선택한 재료를 장보기에 담기 | 공동 레시피, 찜·식단 보강. 외부 글 자동 복제·영양 계산·단위 강제 합산은 포함하지 않는다. |
| 결혼 공간·하객노트 | 양측 구분·관계·초대·참석 상태·인원, 준비할 일, 기존 결혼·여행 앱 연결 | 공동 하객노트. 자동 연락·공개 응답 페이지·축의금 장부 연결은 별도 범위다. |
| 사진첩 | 앨범 이름·외부 HTTPS 보기 링크·메모, 선택적 방문 연결 | 사진 선택·업로드·앱 안의 이미지 보기, 외부 계정의 실제 권한·여유 용량 확인. 링크 권한이나 연결 상태를 자동 검사하지 않는다. |

저장 실패나 다른 탭의 변경에는 입력을 유지하고 최신 로컬 기록을 확인한 뒤 다시 저장하게 한다. 읽기만 한 방문에는 기록을 자동 생성하지 않는다. 실제 공동 저장용 신규 컬렉션·규칙은 후속 구현 범위를 정할 때 설계한다.

일정의 기준은 사용자가 지정한 현재 [공개 Dates](https://CastleRain.github.io/sungso/dates/)이며 브라우저에서 일정 3개를 확인했다. 앞서 과거 소스 8개를 로컬 QA에 표시한 것은 잘못 선택한 검토 자료였다. 해당 사본 표시와 주입 옵션·전용 검사는 폐기했으며, 신혼집 계약 같은 과거 항목을 운영에 추가하지 않았다. Hub와 Dates는 같은 기존 `events` 컬렉션을 읽으므로 운영 일정 복구나 새 시딩은 하지 않는다.

`http://127.0.0.1:8796/sungso/`는 일반 `npm run dev` 서버로 전환해 실제 Google 회원 로그인 뒤 운영 일정을 읽는다. 실제 회원 로그인 뒤 로컬·공개 Dates의 현재 3개 일정이 제목·날짜·이모지·고정 상태까지 일치함을 확인했다. 배포된 홈의 일정 제목·날짜도 기준 기록과 일치했다. 기능 검증은 운영 연결이 차단된 별도 대역을 사용하며 새 생활 앱의 UID별 브라우저 저장 방식은 유지한다.

남긴 말은 앞선 대역의 예시 데이터만 비우고 입력 영역은 유지했다. 사용자 운영 메모를 삭제한 것으로 기록하지 않는다. [생활 앱 통합 검증](../../../life-local-verification.md)은 기존 1,625개 검사 등 이전 결과와 이번 1,623개 검사·서비스 번들 3개·공개 배포·1440px/390px 실제 회원 화면 확인을 구분한다. 실제 배포된 신규 생활 앱 3개에서 빈 기록과 로컬 저장 안내를 확인했으며 운영 데이터 추가·수정·삭제는 실행하지 않았다. [앞선 대문 검증](../../../hub-library-verification.md)도 함께 참고한다.

## NAVER 지도 즐겨찾기와 어디까지 연결할 수 있나

**확인된 기능은 저장 리스트의 공유 링크 열기이며, 개인 저장 목록 전체를 우리 앱으로 자동 동기화하는 공식 API는 이번 공식 문서 조사에서 확인되지 않았다.** 따라서 자동 동기화를 첫 버전의 전제로 삼지 않는다.

| 방식 | 확인 결과 | 계획에 반영할 범위 |
|---|---|---|
| NAVER 저장 리스트 공유 | 공식 고객센터는 일부 공개 이상의 리스트를 공유하고, 받은 링크를 PC 지도·모바일 앱/웹에서 열거나 NAVER 안에 저장할 수 있다고 안내한다. | 사용자가 정한 리스트 링크를 비공개 기록에 저장하고 `네이버에서 보기`로 연다. 링크를 열어 보는 기능이다. 목록 내용의 자동 가져오기·양방향 수정은 포함하지 않는다. |
| NAVER 개인 저장 목록 읽기 | 공식 NAVER API HUB·Maps·로그인 API 목록에서 개인 지도 저장 목록 조회 권한이나 API를 확인하지 못했다. 이는 공개 문서의 확인 범위에 따른 판단이며, 모든 제휴 가능성에 대한 단정은 아니다. | NAVER 로그인만 추가하면 동기화된다고 안내하지 않는다. 비공식 내부 API·스크래핑·쿠키 추출을 사용하지 않는다. |
| 지역 검색 API | NAVER API HUB는 업체·기관 검색 결과를 제공한다. 검색어에 따른 공개 업체 결과이며 사용자의 즐겨찾기 조회가 아니다. | 필요해지면 장소 입력 보조로 별도 검토한다. 우선 장소명·주소·공유 링크를 사용자가 입력할 수 있게 한다. |

근거: [NAVER 지도 리스트 공유/저장](https://help.naver.com/service/5637/contents/21479?lang=ko&osType=COMMONOS), [리스트 이용·공개 범위](https://help.naver.com/service/5637/contents/8259?lang=ko&osType=COMMONOS), [NAVER API HUB 목록](https://api.ncloud-docs.com/docs/naver-api-hub-overview), [Maps API 목록](https://api.ncloud-docs.com/docs/en/application-maps-overview), [NAVER 로그인 API](https://developers.naver.com/docs/login/api/api.md), [현행 지역 검색 API](https://api.ncloud-docs.com/docs/naver-api-hub-search-local). 확인일: 2026-09-14.

공유 리스트의 `일부 공개`는 링크로 공유하는 방식이다. 우리 앱에서 링크를 회원에게만 보여준다고 해서 NAVER 쪽 리스트가 두 계정 전용으로 바뀌지는 않는다. 기존 비공개 리스트를 자동으로 공개 전환하지 않는다. 개인적인 장소가 섞인 목록은 비공개로 유지하고, 사용자가 선택한 개별 장소만 우리 기록에 직접 추가하는 방식도 제공한다.

지역 검색은 [NAVER API HUB 이관 공지](https://developers.naver.com/notice/article/32530)가 있으므로, 향후 구현 시 실제 사용 중인 상품·키·요금·호출 조건을 다시 확인한다. 이 계획을 위해 기존 HomeHunt 키나 서버 설정을 변경하거나 공급자를 시험 호출하지 않았다. 전국 방문 기록은 지역 필터와 지도 링크로 먼저 제공하고, 앱 안의 지도에 점을 표시하는 기능은 지도 서비스 조건을 확인한 뒤 범위를 정한다.

## 사진첩은 무료로 가능한가

**기존 Google Photos 또는 Drive의 무료 여유 용량 안에서 사진을 보관하고, 우리 앱은 방문 기록과 앨범을 연결하는 방식은 가능하다.** 앱 안에서 원본 업로드·공유 갤러리까지 모두 처리하는 기능은 별도 연동 검증이 필요하다. 무료·무제한 보관을 약속하지 않는다.

|---|---|---|

| Google Photos API | 2025-03-31 이후 Library API는 앱이 만든 콘텐츠 중심으로 제한되며, 기존 전체 라이브러리 읽기와 공유 앨범 API 동작이 변경되었다. 사용자가 고르는 사진 접근에는 Picker API가 제시된다. | 기존 앨범 전체 자동 동기화나 영구 썸네일 링크를 보장하지 않는다. 첫 버전은 외부 앨범 열기, 이후 사용자 선택 사진만 다루는 별도 검증이다. [공식 API 변경 안내](https://developers.google.com/photos/support/updates) |
| Render Free 로컬 파일 | 업로드 파일은 재시작·재배포·휴면 진입 시 사라질 수 있고, Free 웹 서비스에는 영구 디스크를 붙일 수 없다. | 사진 원본 보관소로 쓰지 않는다. [공식 Free 제한](https://render.com/docs/free) |

현재 사진 기능은 **앨범 제목·외부 HTTPS 보기 링크·메모**를 저장하고 선택적으로 방문 기록과 연결한다. 연결된 방문의 날짜와 장소를 함께 확인할 수 있다. 사진이 없는 방문도 저장하며, 앨범 연결을 삭제해도 원본 사진을 자동 삭제하지 않는다. 외부 앨범은 사진 서비스에서 열리고, 앱 내부에 원본 이미지가 표시되는 기능은 아직 없다.

앱에서 직접 사진 선택·업로드·미리보기가 꼭 필요하면, 다음 단계에서 [Drive의 파일별 권한 `drive.file`과 Picker](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)를 검토할 수 있다. 이는 공식 API 기능을 바탕으로 한 설계 후보다. OAuth 동의·두 계정의 실제 권한·토큰 만료·할당량·파일 삭제·썸네일 접근을 검증해야 하므로 현재 가능한 것으로 완료 처리하지 않는다. 기존 Firebase Google 로그인에 Drive 권한이 자동 포함되지는 않는다.

사진 원본·썸네일·위치 메타데이터를 GitHub·공개 JSON·배포 자산에 넣지 않는다. 사진을 문자열로 바꿔 Firestore 문서에 넣는 우회도 채택하지 않는다. 현재는 생활 기록을 로컬에만 저장한다. 향후 공동 저장 시 Firestore에는 제한된 크기의 제목·메모·연결 ID 같은 기록만 두고, 기존 앱과 함께 쓰는 무료 사용량을 관리한다. [공식 무료 할당량과 문서 제한](https://firebase.google.com/docs/firestore/quotas). 사진 서비스에 보관된 개인 자료나 권한 링크도 Git·문서·QA 캡처에 남기지 않는다.

## 기록을 한 번만 만들고 여러 화면에서 보기

아래 연결은 현재 같은 UID의 브라우저 로컬 기록에서 사용한다. 공동 저장용 컬렉션은 만들지 않았으며 기존 운영 컬렉션을 재해석하지 않는다.

| 기록 | 한 번 저장할 내용 | 연결하는 화면 |
|---|---|---|
| 장소 | 이름·지역·유형·사용자가 입력한 지도 링크 | 식당, 데이트, 외식 후보 |
| 방문 | 방문 날짜·메모·방문한 장소 ID | 장소별 방문 이력, 데이트 일지, 날짜별 사진 보기 |
| 앨범 연결 | 제목·외부 HTTPS 보기 링크·메모·선택적 방문 ID | 사진첩에서 연결한 방문·장소 확인 |
| 레시피 | 재료·단위·순서·메모 | 레시피 상세, 오늘의 메뉴 |
| 장보기 항목 | 실제로 살 품목·수량·단위·완료 여부·선택적 출처 레시피 ID | 장보기 목록 |
| 하객 | 관계·초대·참석 상태·인원 | 결혼 공간의 하객노트 |

같은 식당을 데이트와 뭐 먹지에서 따로 등록하지 않는다. 장소는 하나이고 방문은 여러 번 쌓인다. 새 방문은 기존 장소를 선택해 연결하며, 자동 병합으로 서로 다른 지점을 합치지 않는다. 사진 원본과 파일 권한은 사진 서비스에서 관리하고 우리 앱은 연결만 관리한다.

레시피에서 장보기로 넘기는 것은 **사용자가 선택한 시점의 구매 항목 생성**이다. 반복 클릭의 중복 생성을 막고, 같은 재료를 합칠 때는 단위와 수량을 확인한다. 이후 레시피 수정이 진행 중인 장보기를 자동으로 바꾸지 않는다. 생활 장보기 금액을 기존 결혼비용 컬렉션에 자동 기록하지 않는다.

일정은 기존 `events`와 Dates, 결혼비용은 기존 WeCost, 여행은 기존 Travel/Honeymoon 계약을 유지한다. 현재 결혼 공간은 기존 앱으로 이동하는 링크를 제공하며, 해당 앱의 운영 기록을 새 로컬 저장소에 복제하지 않는다. 하객노트의 연락처·축의금 같은 추가 항목은 필요 범위를 결정하기 전 수집하지 않는다.

## 구현할 때 지킬 범위와 검증

- Firebase Spark·Render Free를 유지하고, 사진·지도 때문에 새 과금 계정이나 Blaze로 전환하지 않는다.
- 신규 개인 기록은 공통 Google 회원 확인 뒤 로컬에서 읽는다. 향후 공동 저장의 새 규칙은 별도로 확정하며 현재 인증·기존 데이터 계약을 유지한다.
- 앱이 늘어도 대문에서 모든 앱의 전체 데이터를 구독하지 않는다. 생활 앱 사이의 로컬 변경 알림과 계정 종료 시 정리를 유지한다.
- 저장은 사용자 행동에 따라 실행하며, 읽기·샘플 보기·빈 화면 진입으로 개인 데이터를 자동 생성하지 않는다.
- 로컬 저장은 테스트 대역에서 계정 격리·동시 수정·삭제·저장 실패·로그아웃 정리와 초안 보존을 검증한다. 후속 공동 저장은 Emulator에서 별도로 검증하며, 실제 개인 데이터·사진으로 QA 쓰기를 하지 않는다.
- 각 단계는 1440px·390px의 직접 접근·홈 복귀와 연결 앱을 확인하고, 루트 build/test/check 결과 및 미검증 부분을 기록한다.
- 무료 용량 초과·앨범 권한 해제·끊어진 외부 링크가 있어도 텍스트 방문 기록은 유지한다. 외부 원본 삭제나 공유 대상 추가는 자동으로 실행하지 않는다.

**다음:** 장보기·방문 기록의 입력 흐름과 두 계정 공동 저장을 후속 작업으로 구체화한다. 이미지 업로드와 앱 안의 사진 보기는 무료 용량·외부 계정 권한·보관 방식을 확인한 뒤 범위를 정한다. 공동 저장·이미지 조건이 남아 있으므로 이 계획은 active에 유지한다.
