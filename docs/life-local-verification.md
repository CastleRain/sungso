# 운영 일정 기준 정정·생활 앱 기본틀 검증

2026-09-14. 대문과 생활 앱 기본틀을 구성한 뒤, 사용자가 지정한 현재 [공개 Dates](https://CastleRain.github.io/sungso/dates/)를 일정의 기준으로 정정했다. 과거 소스의 8개 일정은 잘못 선택한 검토 자료였으며 현재 일정으로 사용하지 않는다. 이번 릴리스의 로컬 실회원 확인·검사·공개 배포 결과는 아직 확인 대기다. 앞선 대문 개편의 별도 결과는 [대문 검증](hub-library-verification.md)을 따른다.

## 현재 일정 기준과 로컬 화면

- 사용자 요청에 따라 현재 공개 Dates에 저장된 일정만 사용한다. 공개 브라우저에서 일정 행 3개와 과거 사본에 있던 신혼집 계약 항목이 없는 것을 확인했다. 실제 날짜·일정 전문은 문서·공개 자산·QA 캡처에 복제하지 않는다.
- Hub는 `shared/home/home-store.mjs`, Dates는 `apps/dates/js/entry.mjs`에서 같은 운영 `events` 컬렉션을 읽는다. 로컬에 보이던 8개를 운영 DB로 옮기거나 현재 3개를 별도 정적 데이터로 복제하지 않는다. 이번 정정에 운영 일정 추가·삭제·복구 쓰기는 필요하지 않다.
- `http://127.0.0.1:8796/sungso/`는 일반 `npm run dev` 서버로 전환했다. 일정 사본·합성 회원을 주입하지 않으며 실제 Google 회원 로그인 뒤 공개 Dates와 같은 운영 일정을 읽는다. 이 로컬 주소의 실제 회원 로그인과 화면 대조는 아직 확인 대기다.
- 잘못된 사본을 다시 검토 자료로 사용하지 않도록 `QA_PRIVATE_EVENTS_INPUT` 주입 옵션·보조 모듈·전용 검사를 이번 정정에서 제거한다. 일반 합성 QA는 기능 검증용 별도 서버로만 사용한다.
- 일반 개발 서버의 일정·홈·메모 저장은 운영 연결이다. 대역 검증은 운영 연결이 차단된 별도 QA에서 수행하며, 생활 앱의 UID별 브라우저 저장과 구분한다. 앞서 비운 것은 대역의 예시 메모이며 운영 사용자 메모를 삭제한 것이 아니다.

## 대체된 이전 일정 확인 기록

아래 내용은 앞선 로컬 검증 당시의 사실이며 현재 일정의 근거나 복원 결과로 사용하지 않는다. 최초 `8796`에는 QA 합성 일정·메모가 있었고, 이후 과거 소스 `620c1fc`의 초기 일정 8개를 Git 제외 비공개 파일로 준비해 같은 로컬 대역에 표시했다. 당시 확인은 과거 소스와 사본의 일치에 한정됐으며 최신 운영 일정 복구가 아니었다. 사용자가 현재 공개 Dates를 기준으로 지정함에 따라 이 방식은 폐기했다.

당시 운영 DB를 직접 읽으려던 경로는 자동 승인 검토에서 인증정보 접근 사유로 거절되어 실행하지 않았다. 이 과거 접근 실패와 이후 공개 브라우저에서 확인한 현재 일정 3개는 서로 다른 확인 경로다.

## 구현한 생활 앱

| 앱 | 기본 기능 |
|---|---|
| 우리 식탁 `/table/` | 장보기 추가·수정·구매 체크·검색·분류, 레시피 재료·순서, 선택 재료를 장보기에 담기, 레시피·저장 식당에서 먹을 후보 고르기 |
| 우리 발자국 `/footprints/` | 식당·카페·데이트 장소, 가고 싶은 곳·방문 기록, 외부 HTTPS 앨범 링크와 방문 연결 |
| 우리 결혼 `/wedding/` | 하객 구분·관계·초대/참석 상태·동반 인원 집계, 준비할 일, 기존 결혼·여행·일정 앱 연결 |

세 앱은 공통 회원 확인 뒤 `sungso.life.v1.<UID>` 브라우저 저장소를 사용한다. 같은 브라우저·계정에서는 세 앱이 동일한 장소·레시피 등을 참조한다. 상대 계정·다른 기기에 자동 공유되지 않으며 UI에도 이 범위를 표시한다. 빈 상태의 조회·추천은 저장하지 않는다. 신규 Firestore 컬렉션·인증·규칙·요금제 변경은 없다.

여러 탭의 저장은 Web Locks와 revision 비교로 보호한다. 지원하지 않는 브라우저, 손상된 원본, 용량 부족, 계정 변경에는 저장을 차단하고 원본을 보존한다. 다른 탭 변경 중 열린 편집은 입력을 유지하며 최신 상태를 검토한 뒤 저장한다. 로그아웃은 DOM·구독·모달을 정리하고 저장된 로컬 기록은 지우지 않는다.

사진첩은 외부 앨범 링크만 저장한다. 이미지 업로드·앱 안의 사진 표시·NAVER 즐겨찾기 자동 동기화·공동 기록 저장은 후속 범위다. 외부 링크의 접근 권한이나 실제 연결 성공을 확인한 것은 아니다.

홈의 원래 6개 앱 ID와 공유 설정 계약은 보존한다. 모든 앱은 별도 생활 앱 목록을 합쳐 9개이며, 모바일에서는 6개와 3개 두 페이지로 탐색한다. 신규 3개는 현재 공유 홈 바로가기 편집 대상에 넣지 않는다.

## 이전 로컬 구현의 브라우저 검증

다음은 일정 기준 정정 전 검증 기록이다. 생활 CRUD는 별도 합성 QA `8797`에서 수행해 당시 검토용 대역 `8796`의 빈 생활 목록과 분리했다. 합성 회원과 테스트 제목만 사용했고 운영 DB·공급자 연결은 차단했다. 지금 일반 개발 서버로 전환한 `8796`의 실제 회원 검증을 뜻하지 않는다.

- 장보기 품목 추가·완료 체크·분류를 확인했다. 레시피 재료 3개 중 2개를 선택해 장보기 총 3개가 되었고, 뭐 먹지에 같은 레시피와 우리 발자국 식당이 함께 표시됐다.
- 장소를 등록하고 방문 날짜·이야기, 그 방문에 연결한 외부 앨범 링크를 저장했다. 장소 카드의 방문 횟수와 앨범 카드의 장소·날짜 연결을 확인했다. 링크는 외부로 열지 않았다.
- 하객 동반 인원 3명을 참석으로 저장해 전체 3명·참석 예정 3명 집계를 확인했다. 준비 메모 완료 체크와 수정·삭제 취소 시 원본 보존을 확인했다.
- 새로운 탭에 다시 로그인해 생활 기록이 유지됨을 확인했다. 다른 탭에서 준비 메모를 추가하면 열려 있던 장보기 편집의 입력을 보존하고 저장을 막았으며, 최신 상태 검토 후 저장하면 양쪽 변경이 모두 남았다.
- 소희 대역 계정은 빈 목록, 성우 대역 계정으로 복귀하면 기존 3개 품목이 다시 나타났다. 운영 사용자 계정으로 저장한 결과가 아니다.
- 1440px에서 세 생활 앱의 진입·연결, 390px에서 장보기·방문/앨범·하객 입력을 확인했다. 확인한 화면에서 가로 넘침은 없었다.
- 모든 앱은 390px에서 실제 1/2·2/2 페이지 이동, 장보기 검색 1개, 검색을 비운 뒤 1440px에서 9개와 페이지 숨김을 확인했다. 최종 QA 탭의 경고·오류 로그는 0건이었다.
- 당시 검토용 홈은 1440×900px에서 콘텐츠 하단 666.59px·문서 높이 900px, 390×700px에서 하단 605.89px·문서 높이 700px였다. 메모 예시는 없고 중요 일정·다가오는 3개·전체 8개 링크가 보였다. 이 일정 사본은 현재 기준에서 제외했다.
- 당시 검토용 Dates에서 과거 사본 8개의 표시와 합성 약속 이름 제거를 확인했다. 개인 일정 전문을 QA 결과에 복사하지 않았으며, 이 결과를 현재 운영 일정의 확인으로 사용하지 않는다.

두 QA 서버의 이 작업 종료 시 DB 대역 쓰기·트랜잭션·운영 요청·공급자 요청은 모두 0건이다. 생활 앱의 명시적인 브라우저 로컬 저장은 수행했으며 이 수치에 포함되는 DB 쓰기와 구분한다. 앞선 대문 검사의 대역 쓰기 5건은 별도 세션의 결과다.

## 남은 범위

현재 공개 Dates의 3개 일정은 브라우저에서 확인했다. 일반 개발 서버의 실회원 화면 대조, 이번 릴리스 검사와 공개 배포·자산 대조는 확인 대기다. 운영 일정 복구 쓰기는 수행하지 않는다. 공동 저장과 이미지 기능은 [생활 앱 계획](development-plans/active/couple-life/README.md)에서 이어간다. 실제 기기/회원 저장, 외부 앨범 권한·업로드, JSON 백업 파일의 내려받기/복구 왕복은 검증하지 않았다. 기존 개인 홈 계획의 키 폐기·남은 회원 QA·PDF 보류도 별도로 유지한다.

**다음:** 현재 운영 일정 기준으로 로컬·배포 결과를 확인한 뒤, 두 계정이 같은 생활 기록을 보는 공동 저장을 다음 구현 범위로 정한다.
